# Technical Spike — 핵심 가치 프로토타입

| 항목 | 내용 |
|---|---|
| 문서 상태 | **Draft v0.3**. 창업자가 2026-11-15에 이 Spike의 범위를 여기서 마감하라고 지시했다. 검증 기준을 다 채우지 못한 채 닫는다 (11장). 코드와 지시문은 그대로 남긴다 |
| 검증하는 Gate | F-02, F-03, F-04, F-05 (S2·S3·S4·S5b를 하나로 묶음) |
| 관련 결정 | D-013, D-014, D-015, D-016 / `docs/architecture/technical-discovery.md` 0.1절 3번 |
| 형태 | 격리된 실험 코드 (`spikes/core-prototype/`). 제품 코드가 아니다 |

## 1. 목적

실제 뉴스 하루치로 **"나에게 맞는 소식 몇 편"을 끝까지 만들어 폰에서 읽어 본다.** 세 핵심 가치 가운데 Personal Relevance와 Meaningful Understanding이 실제로 느껴지는지를 처음으로 직접 확인하는 것이 목적이다. 새(Emotional Experience)는 S6에서 따로 만들어 이 읽기 화면에 붙인다.

창업자의 질문에도 답한다: 지금 본 인터랙티브 품질이 Sonnet이나 GPT 경량 모델로 만들어도 나오는가.

## 2. 만드는 것

| 단계 | 하는 일 | 남기는 기록 |
|---|---|---|
| 1 수집 | newsapi.ai에서 그날의 사건 목록과 후보 사건의 기사 본문을 받는다. 본문의 군더더기를 정리한다 | 매체, 발행 시각, 원문 주소 |
| 2 사건 정리 | 공급원의 사건 묶음을 쓰되, 같은 기사가 여러 매체에 실린 것과 잘못 묶인 것을 보정한다 | 사건별 기사 목록 |
| 3 후보 평가 | 사건마다 내 프로필의 어떤 항목과 사건의 어떤 사실이 이어지는지 찾고, 관련성·중요성·새로움·다양성·신뢰성을 평가한다. 근거가 없으면 연결을 만들지 않는다 | 연결고리(프로필 항목, 사건 사실, 추론 여부), 5개 기준 평가 |
| 4 선정 | 평가 결과로 오늘의 소식을 고른다. 수량은 설정값이다 | 모든 후보의 선정·제외 이유 |
| 5 집필 | 기사에서 사실 목록을 먼저 뽑고, 그 사실만으로 소식을 쓴다. 배경지식과 개념 설명은 AI 지식으로 쓰되 사건의 사실과 구분한다. 다른 모델이 문장과 근거를 대조한다 | 문장과 근거의 연결, 검증 결과 |
| 6 인터랙티브 | AI가 설명 목적에 맞는 유형을 고르고 스펙을 만든다. S5a의 검증기로 거르고, 실패하면 요약 카드로 대체한다 | 고른 유형과 이유, 검증 결과, 들어간 요소의 종류 |
| 7 읽기 화면 | 폰에서 오늘의 소식을 순서대로 읽고 끝나는 화면. 진행 위치(2/N)와 종결 | — |
| 8 모델 비교 | 3·5·6단계를 같은 입력으로 여러 모델(상위 모델, Sonnet급, 경량 모델)에 돌려 품질과 비용을 나란히 비교한다 | 모델별 결과, 검증 통과율, 호출 비용과 시간 |

모든 단계의 입력과 출력, 쓴 모델과 지시문 버전, 비용과 시간을 맥북 안의 파일 DB에 남긴다. "왜 이 소식이 뽑혔는지"를 거슬러 볼 수 있게 하기 위해서다.

## 3. 만들지 않는 것

프로필 입력 화면(프로필은 맥북의 글 파일로 둔다), 접근 제어, 평가 화면, 지난 소식, 키워드 기준선 비교, 독립 표본 대조, 관계도 유형, 자료사진, 정책과 규약. 프로토타입을 써 본 뒤 정식 개발 절차에서 다룬다.

## 4. 검증 기준

| # | 기준 | 확인 주체 |
|---|---|---|
| 1 | 실제 뉴스 하루치가 수집부터 폰 읽기 화면까지 끝까지 이어진다 | 실행 기록 |
| 2 | 전달된 모든 소식에 추천 이유가 있고, 프로필의 특정 항목과 사건의 특정 사실을 가리킨다. 근거가 없는 사건에는 개인화된 이유가 붙지 않는다 | 기록 점검 + 창업자 |
| 3 | 소식의 사실·숫자·인용이 사실 목록에 연결되어 있고, 사실 목록은 기사 원문에 연결되어 있다 | 기록 점검 |
| 4 | 모든 소식에 인터랙티브 설명이나 대체 시각 요소가 들어 있다. 글자만 있는 소식이 없다 | 기록 점검 |
| 5 | 서로 다른 날짜로 세 번 이상 돌려 본다 | 실행 기록 |
| 6 | 모델별 비교표가 있다: 연결고리와 인터랙티브 스펙의 검증 통과율, 창업자의 눈가림 평가, 비용과 시간 | 기록 + 창업자 |
| 7 | 창업자가 폰에서 읽고 "나와 관련 있는가, 이해가 되는가, 인터랙티브가 도움이 되는가"를 소식마다 평가한다 | 창업자 |
| 8 | LLM 호출 비용 합계가 10만 원 이내다. 호출마다 비용을 기록하고 8만 원에 이르면 멈추고 보고한다 | 기록 |

기준 2, 6, 7은 창업자가 직접 읽고 평가하기 전에는 통과로 보고하지 않는다 (P-12). 이 Spike의 통과는 MVP 합격이 아니다.

## 5. 필요한 것

- Anthropic API 키 (`.env`의 `ANTHROPIC_API_KEY`)
- GPT 경량 모델도 비교하려면 OpenAI API 키 (`.env`의 `OPENAI_API_KEY`). 없으면 Anthropic 모델끼리만 비교한다
- 창업자의 프로필: `private/profile.md`에 자유롭게 적는다. 건강·재정 같은 민감한 내용과 이름·연락처는 적지 않는다

## 6. 규모

키와 프로필을 받은 뒤 2~4일. 1·2단계(수집, 사건 정리)는 키 없이 먼저 만들 수 있다.

## 7. 결과 (2026-11-15, 진행 중)

창업자가 2026-11-15에 Gemini 키와 프로필을 주며 착수를 지시했다 ("일단 이걸로 하자"). Claude와 GPT 키는 나중에 받는다. 그래서 모델 비교는 우선 Gemini 모델끼리 한다.

**만든 것** (`spikes/core-prototype/`)

- `run.mjs`: 프로필 스냅숏 → 수집 → 1차 선별 → 기사 받기와 중복 제거 → 사실 목록 → 후보 평가 → 선정 → 집필 → 검증 → 인터랙티브 → 오늘의 소식. 단계마다 결과를 `private/runs/<실행ID>/`에 남기고, AI 호출마다 입력·출력·모델·지시문 버전·토큰·시간·비용을 남긴다
- `render.mjs`: 폰 읽기 화면 (진행 위치, 추천 이유, 본문, 조작형 설명 또는 요약 카드, 출처, 종결 화면)
- `config.json`: 소식 수, 평가 비중, 단계별 모델, 비용 상한
- 구조로 막아 둔 것: 연결고리의 프로필 근거는 이번 스냅숏에 실제로 있는 항목만 인정한다. 사실은 근거 문장이 기사 원문에 글자 그대로 있을 때만 남긴다. 사실 문장의 숫자는 근거 사실에 있는 숫자여야 한다. 선정은 AI가 아니라 정해진 규칙이 한다. 조작형 설명은 S5a 검증기를 통과해야 쓴다

**확인한 것 (AI 호출 없이 할 수 있는 범위)**

| 항목 | 결과 |
|---|---|
| 프로필 해석 | 창업자 프로필에서 12개 항목 (하는 일 1, 관심사 3, 생활 맥락 2, 고민과 계획 1, 아는·모르는 분야 2, 받고 싶지 않은 소식 3) |
| 본문 정리 | 표본 100건에서 평균 1,401자 → 1,334자. 정리 뒤 군더더기 문구가 남은 기사 0건 |
| 읽기 화면 | 가짜 사례 3편으로 360×780 화면 확인: 진행 위치 1/3 → 3/3 → 종결 화면, 조작형과 요약 카드가 본문 안에 들어감, 가로 넘침 없음 |

**첫 실행 (2026-11-15, 창업자가 크레딧을 충전한 뒤)**

창업자 지시로 주 모델을 gemini-4-hydrogen으로 두었다 ("경량모델로 시험… hydrogen으로 해보자"). 검증만 집필과 다른 모델(gemini-3.8-flash)이 한다.

| 실행 | 결과 | 비용 |
|---|---|---|
| r1 | 후보 55건 → 선정 1편 → 검증에서 보류, 발행 0편 | 0.32달러 |
| r2 (수정 뒤) | 후보 252건 → 깊이 평가 12건 → 선정 3편(모두 근거 있는 개인 연결) → 3편 발행, 조작형 3개(과정 2, 비교 1) 모두 첫 시도에 검증 통과 | 0.64달러, AI 호출 43회 |

r1에서 찾아 고친 것 세 가지:
1. 사건별 기사를 받는 호출이 잘못돼 엉뚱한 기사가 섞였다 (10건 중 5건이 "다른 사건이 섞임"으로 제외). `event/getEvent`로 바꿨다.
2. 프로필 검색어가 두 단어 구절이라 10개 중 6개가 결과 0건이었다. 한 단어 위주, 최근 3일, 14개로 바꿨다 (검색 후보 13건 → 210건).
3. 검증자가 쉬운 말로 바꿔 쓴 문장까지 걸렀고, 걸리면 바로 버렸다. 판정 기준을 고치고, 걸린 문장은 필자에게 한 번 돌려보내 고쳐 쓰게 한 뒤 다시 검증한다 (지시문 버전 p2).

r2의 소식: 구글 딥마인드 '알파게놈 2' 공개 · 고지방 식단과 장 줄기세포 연구 · AI 시대 기업이 원하는 인재. 세 편 모두 프로필의 서로 다른 항목과 이어졌다 (어느 항목인지는 `private/runs/r2/`의 기록에 있다). 읽기 화면: https://claude.ai/artifact/FsDCDXKnRPVUqg7ydcrAPr (비공개)

r2 단계별 비용(달러): 1차 선별 0.12 · 사실 목록 0.26 · 평가 0.12 · 집필 0.05 · 고쳐 쓰기 0.01 · 검증 0.02 · 인터랙티브 0.06. 걸린 시간 약 2분. 누적 LLM 비용 0.95달러. 뉴스 토큰 누적 67 / 2,000.

**아직 확인하지 못한 것**: 창업자의 평가(기준 2, 7), 다른 날짜 반복(기준 5, 지금 1일치), 모델 비교(기준 6), Claude·GPT 모델.

## 8. 관찰한 한계

- 하루치 한 번만 돌렸다. 기준 1은 한 번 이어졌고, 나머지는 창업자 평가와 반복 실행 전이다.
- r2의 3편 중 2편은 매체 한 곳의 보도만 근거다 (신뢰성 점수는 낮게 매겨졌으나 선정을 막지 않았다).
- 조작형 3개 중 2개가 '과정' 유형이다. 순서가 뚜렷하지 않은 소식(모델 공개)에도 과정 유형을 골랐다. 값을 바꿔 보는 시뮬레이션은 한 번도 나오지 않았다.
- 추천 이유에 프로필보다 조금 더 나간 표현이 검증을 통과한 사례가 있다 (프로필에 관심사로만 적힌 것을 매일 하는 습관처럼 썼다).
- 뉴스 공급원의 큰 사건 목록은 연예·사건사고·정치 위주라 이 프로필에는 거의 쓸모가 없었다. 선정 3편 모두 프로필 검색에서 나왔다.
- 과정 유형의 단계 설명 문장과 배경·용어 풀이 문단은 검증기가 사실 여부를 보지 않는다 (창업자 방향: 배경지식은 AI 지식으로 쓴다).
- 수치가 있는 사실의 값(예: "3만 2천 대" → 32000)이 원문과 맞는지는 코드로 대조하지 못한다. 근거 문장에 숫자가 있는지만 본다.
- 프로필 항목은 줄 단위로 나눠서, 한 줄에 여러 사실이 든 항목("하는 일")은 한 덩어리로 다뤄진다.
- 새(S6)는 아직 없다.

## 9. 배운 점 (2026-11-15, r1·r2 기준)

하루치 두 번의 실행에서 나온 것이다. 반복 실행 전이라 확정된 결론이 아니다. Technical Design의 입력으로 쓴다.

| # | 배운 점 | 근거 | 반영 |
|---|---|---|---|
| 1 | **후보를 어디서 모으느냐가 품질을 가장 크게 좌우한다.** 공급원의 "큰 사건" 목록은 연예·사건사고·정치 위주라 이 프로필에는 거의 쓸모가 없었다 | r2 선정 3편이 모두 프로필 검색에서 나왔다. 큰 사건 44건 중 선정 0건 | 미반영. 후보 수집 구조(큰 사건의 비중, 주제별 수집)는 반복 실행 뒤 다시 본다 |
| 2 | 검색어는 한 단어의 구체적인 이름이어야 한다. 두 단어 구절은 결과가 없다 | r1 검색어 10개 중 6개가 0건. 고친 뒤 검색 후보 13건 → 210건 | p2 반영 |
| 3 | 외부 공급원 호출은 받은 내용이 요청과 맞는지 확인해야 한다. 틀린 호출도 오류 없이 그럴듯한 기사를 돌려준다 | r1에서 사건별 기사에 무관한 기사가 섞여 10건 중 5건 제외 | 코드 수정. 사실 목록 단계의 "다른 사건이 섞였는가" 판정이 이를 잡아냈다. 이 판정은 유지한다 |
| 4 | 검증은 "버리기"만으로는 부족하다. 걸린 문장을 필자에게 돌려보내 고쳐 쓰게 하고 다시 검증해야 발행할 것이 남는다 | r1 발행 0편, r2 첫 검증 1편 → 고쳐 쓰기 넣은 뒤 3편 | p2 반영 (고쳐 쓰기 1회 → 재검증) |
| 5 | 검증자에게 "엄격하게"만 지시하면 쉬운 말로 바꿔 쓴 것까지 거른다. 무엇이 문제이고 무엇이 아닌지 문장 종류별로 알려 줘야 한다 | r1에서 요약·풀어 쓰기 문장이 overreach 판정 | p2 반영 |
| 6 | 추천 이유는 프로필에 적힌 것보다 더 나가기 쉽고, 검증자도 놓친다 | r2에서 관심사로만 적힌 항목을 매일 하는 습관처럼 쓴 문장이 검증을 통과 | p3 반영: 집필·검증 지시문에 "빈도·습관·정도를 보태지 않는다" 명시. 효과 미확인 |
| 7 | AI는 조작형 유형으로 '과정'을 쉽게 고른다. 순서가 없는 소식도 여러 장으로 나눠 과정이라 한다. 시뮬레이션은 나오지 않았다 | r2 조작형 3개 중 과정 2, 비교 1, 시뮬레이션 0 | p3 반영: 유형 선택 순서(시뮬레이션 → 비교 → 과정)와 "순서를 바꿔도 말이 되면 과정이 아니다" 기준 추가. 효과 미확인 |
| 8 | 매체 한 곳의 보도만으로도 선정된다 | r2 3편 중 2편이 단일 매체 | p3 반영: 단일 매체면 신뢰성 3점 이하. 선정 규칙에서 막을지는 미결정 |
| 9 | 사실 목록의 "근거 문장은 원문에 글자 그대로" 규칙은 잘 지켜진다 | r1 100건, r2 130건 모두 원문 대조 통과, 버린 것 0건 | 유지 |
| 10 | 비용의 대부분은 글쓰기가 아니라 앞 단계(선별·사실 목록·평가)에서 나온다 | r2 0.64달러 중 선별 0.12, 사실 목록 0.26, 평가 0.12, 집필 0.05 | 미반영. 앞 단계에 더 가벼운 모델을 쓰는 것이 모델 비교의 주요 대상이다 |

지시문 버전: p1(첫 실행) → p2(2, 4, 5번) → p3(6, 7, 8번, 그리고 10장의 표현 시트). **p3의 6, 7, 8번 변경은 실행해 보지 않았다.** p3으로 실행한 것은 표현 시트뿐이다.

## 10. 창업자가 제시한 목표 시안 (2026-11-15)

창업자가 r2의 읽기 화면을 읽은 뒤, 같은 소식을 GPT 상위 모델에게 다시 꾸미게 한 시안을 주며 방향을 정했다.

> "내가 원하는 결과값은 이래. … 우리의 목표는 저비용의 경량모델로도 저정도 퀄리티의 뉴스콘텐츠를 사용자가 받을수있게하는거야."

- 저장한 곳: `docs/research/references/target-edition-mockup.html` (브라우저로 열면 된다). 추천 이유 문장 세 개는 창업자의 실제 프로필에서 나온 내용이라 저장소 사본에서 가렸다. 원본은 `private/references/`에 있다.
- 이 시안은 **우리 r2 결과(11-edition.json)를 한 글자도 바꾸지 않고 그대로 넣었다.** 달라진 것은 두 가지뿐이다: (가) 화면 구성과 디자인, (나) 소식마다 손으로 덧붙인 짧은 글감 한 묶음.

### 10.1 시안이 우리 화면과 다른 점 (핀트)

| # | 시안 | 우리 r2 화면 |
|---|---|---|
| 1 | **글이 아니라 조작이 주인공이다.** 순서가 "한눈에 요점 → 직접 눌러 보기 → 확인 문제 → (원하면) 깊이 읽기"다. 긴 본문은 '깊이 읽기'를 눌러야 나온다 | 긴 본문이 주인공이고 조작형 설명은 본문 중간에 낀 부속물이다 |
| 2 | **질문으로 연다.** "식단을 바꿔도, 세포는 기억할까?"처럼 궁금증을 먼저 세우고 한 문장으로 답한다 | 기사 제목과 첫 문장으로 연다 |
| 3 | **대표 숫자 하나를 크게 보여 준다** ("16% → 30%", "18%", "38%p"). 숫자가 무엇인지 한 줄로 붙인다 | 숫자가 문장 속에 묻혀 있다 |
| 4 | **핵심 사실 3줄**을 카드로 먼저 준다 (30초 안에 요점) | 없음 |
| 5 | **확인 문제 하나.** 암기가 아니라 잘못 읽기 쉬운 지점을 묻는다 ("이 연구로 사람의 암 위험이 같은 비율만큼 높아진다고 말해도 될까요?") | 없음 |
| 6 | **오해를 막는 한 줄**을 조작 화면 바로 옆에 둔다 ("연구 대상은 생쥐", "같은 질문·같은 집단의 결과가 아니다") | 본문 끝의 '아직 확실하지 않은 점' 한 줄 |
| 7 | 주제마다 색과 아이콘, 큰 명조 제목, 도넛·막대 같은 그림. 잡지 같은 인상 | 한 가지 색의 글 위주 화면 |
| 8 | 용어 풀이는 눌러서 펼친다. 사실·개념·해석을 딱지로 구분한다 | 용어는 끝에 나열. 구분 딱지는 있음 |
| 9 | 첫 화면에서 세 편을 한눈에 보고 고른다 (카드마다 한 줄 요약, 대표 숫자, 작은 그림) | 정해진 순서로 한 편씩 |

시안에서 **그대로 가져오지 않는 것**: '나중에 읽기'(저장)와 '핵심 요약 복사'(공유)는 PRD의 제외 범위다 (PRD 7장, Brief 9.8). 첫 화면에서 골라 읽는 방식은 PRD의 "정해진 수를 읽고 끝난다"는 종결 경험, 새(Emotional Experience)와 함께 다시 설계해야 한다. 시안에는 새가 없다. 영어 꼬리표("YOUR DAILY SIGNAL")는 취향 확인이 필요하다.

### 10.2 여기서 나온 설계 결정 (Proposed)

1. **품질의 큰 몫은 모델이 아니라 화면 틀에서 나온다.** 시안이 좋아 보이는 이유의 대부분은 구성과 디자인이고, 이것은 한 번 만들어 두면 매일 AI 비용이 들지 않는다. 그래서 "좋은 화면 틀은 사람이(또는 상위 모델로 한 번) 만들고, 경량 모델은 매일 그 틀의 빈칸만 채운다"를 기본 구조로 삼는다. 조작형 설명에 쓰던 "승인된 컴포넌트 + 구조화 데이터"(D-016) 방식을 소식 한 편 전체로 넓히는 것이다.
2. **표현 시트를 파이프라인의 한 단계로 둔다.** 검증을 통과한 소식에 대해 질문형 제목, 한 문장 답, 대표 숫자, 핵심 사실 3줄, 카드용 한 줄, 오해 방지 한 줄, 확인 문제, 주제 색을 만든다. 모든 항목은 사실 ID를 달고, 숫자는 코드로 대조한다.
3. **읽기 순서를 바꾼다**: 요점 → 조작 → 확인 문제 → 깊이 읽기(선택). 긴 본문은 기본으로 접는다.
4. 조작형 설명은 본문의 부속물이 아니라 소식의 중심 화면으로 설계한다. 컴포넌트마다 큰 숫자, 그림, 주의 문구 자리를 갖춘다.

### 10.3 경량 모델이 표현 시트를 채울 수 있는가 (한 번 시험)

`present.mjs`로 r2의 3편에 대해 두 모델에게 표현 시트를 만들게 했다 (`private/runs/r2/12-present.json`).

| 모델 | 3편 중 코드 대조 통과 | 한 편당 비용 | 관찰 |
|---|---|---|---|
| gemini-4-hydrogen | 3 | 약 0.008달러 | 질문·대표 숫자·핵심 3줄·확인 문제가 시안과 비슷한 수준. 확인 문제가 오해 지점을 묻는다 |
| gemini-3.5-flash-lite | 2 | 약 0.002달러 | 쓸 만하다. 1편에서 "1억 700만"을 "1억 7천만"으로 잘못 썼고 **코드 대조가 잡았다.** 확인 문제 3개 중 2개는 단순 암기형이었다 |

한계: 한 번, 3편뿐이다. 지시문의 예시 문장("식단을 바꿔도, 세포는 기억할까?")이 같은 소식에 그대로 나왔으므로 그 한 편은 모델의 실력으로 볼 수 없다. 표현 시트는 읽기 화면에 연결하지 않았다 (`render.mjs`는 r2 때의 화면 그대로다). 시안 수준의 화면 틀은 만들지 않았다.

## 11. 마감 시점의 상태 (2026-11-15)

창업자 지시로 이 Spike의 범위를 여기서 닫는다. 4장의 검증 기준 대비 상태는 다음과 같다.

| # | 기준 | 상태 |
|---|---|---|
| 1 | 수집부터 폰 읽기 화면까지 이어진다 | 한 번 확인 (r2) |
| 2 | 모든 소식에 근거 있는 추천 이유 | 기록상 3편 모두 프로필 항목과 사실 ID가 연결됨. 과장 표현 1건이 검증을 통과함 |
| 3 | 사실·숫자가 사실 목록과 원문에 연결 | 기록상 확인 (사실 230건 모두 원문 대조 통과) |
| 4 | 글자만 있는 소식 없음 | r2 3편 모두 조작형 설명 포함 |
| 5 | 서로 다른 날짜 세 번 | **미달** (하루치 1회) |
| 6 | 모델별 비교표 | **미달** (표현 시트만 두 모델 비교. Claude·GPT 모델은 키가 없어 못 함) |
| 7 | 창업자의 소식별 평가 | 창업자가 읽었고, 평가 대신 목표 시안으로 방향을 주었다 (10장) |
| 8 | LLM 비용 10만 원 이내 | 누적 0.98달러 |

이 Spike의 결과는 기술 선택을 확정하지 않는다 (Decision Log 5). 다음 단계와 이어받는 방법은 `docs/architecture/technical-discovery.md` 0.3절에 있다.
