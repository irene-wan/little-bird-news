# Technical Spike S5a — 인터랙티브 컴포넌트와 검증 하네스

| 항목 | 내용 |

| 관련 결정 | D-007, D-024, D-025, D-039 (Confirmed) · D-016 (Validation Required) · D-022 (Pending) / PRD FR-D-01~12, FR-D-15~17, NFR-P-02, NFR-U-03, AC-MU-05~06, AC-MU-10 |

## 1. 목적

"승인된 컴포넌트에 검증된 구조화 데이터를 전달하는 방식"(D-016, B§9.5)이 모바일 웹에서 성립하는지 확인한다. 이 Spike는 **AI가 스펙을 만드는 부분을 다루지 않는다.** 사람이 쓴 스펙으로 컴포넌트, 검증 방법, 실패 시 대체 사슬을 먼저 확인한다. AI의 스펙 생성은 S5b에서 다룬다.

## 2. 범위

**포함**

- 인터랙티브 표현 유형 후보의 컴포넌트 시제품. 네 유형(관계, 과정, 비교, 시뮬레이션) 가운데 **비교, 시뮬레이션, 과정을 먼저 시험하고, 관계는 시간이 남으면 시험하는 것을 제안한다.** 관계도는 좁은 화면에서의 배치가 가장 어려울 것으로 보아 뒤에 두었다. 순서는 브리프 승인 때 바꿀 수 있다
- 컴포넌트에 전달하는 구조화 스펙의 형식 초안: 수치마다 사실 ID를 달거나 가정값으로 표시한다 (FR-D-05), 데이터의 출처와 기준 시점을 담는다 (FR-D-11)
- 고정 기술 테스트 사례 (D-024): 유형마다 2건, 서로 다른 주제 영역으로 구성한다. **내용은 실험용으로 지어낸 가짜 내용이며 실제 보도를 쓰지 않는다**
- 검증 하네스
  - 스펙 형식 검사
  - 수치의 사실 참조 검사 (사실 ID가 없고 가정값 표시도 없는 수치를 거른다)
  - 조작 결과 계산의 검사: 같은 입력에 대해 따로 계산한 값과 화면의 값을 대조한다 (FR-D-04)
  - 자동 조작 검사: 값을 바꾸면 결과가 달라지는지 (FR-D-03)
  - 화면 크기별 잘림·겹침 검사 (NFR-U-03)
- 대체 사슬: 스펙 오류와 표시 실패를 일부러 일으켜, 깨진 화면 대신 같은 사실 목록에서 그린 정적 시각 콘텐츠(표, 수치 카드 등)가 나오는지 확인한다. 실패가 기록되는지 확인한다 (FR-D-08, AC-MU-10)
- 실기기에서의 터치 조작, 스크롤과의 충돌 (FR-D-07)

**제외**

- AI의 유형 선택과 스펙 생성 (S5b)
- 실제 뉴스 데이터
- 자료사진을 이용한 대체 (사진 권리는 S1에서 다룬다)
- 최종 디자인, 제품 코드로의 통합
- 컴포넌트 종류와 구현 기술의 확정 (D-016은 창업자가 결정한다)
- 이해에 도움이 되는지의 평가. 이 Spike는 기술 동작만 본다. 이해 기여는 따로 평가한다 (FR-D-14)

## 3. 방법

1. 고정 기술 테스트 사례를 가짜 내용으로 작성하고, 사례마다 사실 목록과 스펙을 손으로 쓴다.
2. 컴포넌트 시제품을 만들고 스펙으로 표시한다. Spike에 쓰는 도구는 속도를 기준으로 고르고 결과 문서에 기록한다. 이 선택은 제품 스택 결정(T-10)과 무관하다.
3. 검증 하네스를 만들어 정상 사례와, 일부러 틀리게 만든 사례(틀린 수치, 형식 오류, 참조 없는 수치, 틀린 계산)를 돌린다.
4. 표시 실패를 일으켜 대체 사슬을 확인한다.
5. 창업자가 실기기에서 직접 조작한다. 자동 검사 결과와 실기기 확인을 구분해 기록한다.

## 4. 검증 기준

| # | 기준 | 확인 주체 |
|---|---|---|
| 1 | 서로 다른 2가지 이상의 인터랙티브 방식이 실기기에서 동작한다. 값이나 선택지를 바꾸면 결과가 달라진다 | 실기기, 창업자 |
| 2 | 조작과 화면 스크롤이 서로 방해하지 않는다. 한 손으로 조작할 수 있다 | 실기기, 창업자 |
| 3 | 일부러 넣은 오류(틀린 수치, 형식 오류, 참조 없는 수치, 틀린 계산)를 검증 하네스가 걸러 낸다. 걸러 내지 못한 종류가 있으면 그대로 기록한다 | 자동 검사 |
| 4 | 가정값이 실제 수치와 구분되어 표시되고, 데이터의 출처와 기준 시점이 표시된다 | 화면 확인 |
| 5 | 스펙 오류나 표시 실패를 일으켰을 때 깨진 화면도 글자만 있는 화면도 나오지 않고 대체 시각 요소가 나온다. 실패가 인터랙티브 실패로 기록된다 | 강제 실패 시험 |
| 6 | 정한 화면 크기 범위에서 잘림과 겹침이 없다. 범위는 결과에 기록한다 | 자동 검사 + 실기기 |
| 7 | 조작하지 않아도 사례의 핵심을 알 수 있다 (FR-D-10) | 화면 확인 |

기준 1~2는 창업자의 실기기 확인 없이는 통과로 보고하지 않는다 (P-12). 이 Spike의 통과는 AC-MU-05의 합격이 아니다. AC-MU-05는 자연 추천 소식에서의 결과까지 요구한다.

## 5. 산출물

- 스펙 형식 초안
- 검증 하네스와 주입 오류 검출 결과
- 유형별 구현 난이도와 모바일 조작에서 관찰한 문제
- D-016에 대한 선택지 정리 (Proposed)

- 먼저 시험할 유형의 순서에 이견이 있으면 브리프 승인 때 알려 준다.

## 8. 결과 (2026-11-14, 진행 중)

창업자가 2026-11-14에 착수를 승인했다 ("그렇게 해"). 코드는 `spikes/interactive-components/`에 있다. 시험 페이지는 창업자 계정의 비공개 Artifact로 게시했다: https://claude.ai/artifact/HhzkguHu15MrpGc9cY1yS9

**만든 것**

- 컴포넌트 시제품 세 가지: 비교(대상 전환 + 막대), 시뮬레이션(슬라이더 + 계산 결과), 과정(단계 넘기기)
- 고정 기술 테스트 사례 6건 (유형마다 2건, 주제 영역: 주거, 교통, 금융, 노동, 제도, 소비자 안전). 모두 지어낸 가짜 내용
- 스펙 형식 초안: 모든 수치에 사실 ID 또는 가정값 표시, 계산식은 사칙연산만 허용하고 코드를 실행하지 않음, 계산 결과마다 대조값
- 검증 하네스 (`harness.mjs`), 대체 시각 요소(사실 목록으로 그린 요약 카드), 실패 기록
- Spike에 쓴 도구: 라이브러리 없는 웹 표준(HTML, CSS, JavaScript)과 Node. 제품 스택 결정과 무관하다

**검증 기준별 상태**

| # | 기준 | 상태 | 근거 |
|---|---|---|---|
| 1 | 실기기에서 2가지 이상 동작 | **미확인** | 개발 환경의 360×780 화면에서 세 가지가 모두 동작했다. 갤럭시 S23에서의 확인은 창업자가 해야 한다 |
| 2 | 조작과 스크롤이 서로 방해하지 않음, 한 손 조작 | **미확인** | 실제 손가락 터치는 개발 환경에서 확인할 수 없다. 누르는 영역은 모두 44px 이상으로 만들었다 |
| 3 | 주입 오류를 하네스가 걸러 냄 | 확인 | 정상 사례 6건 통과, 주입 오류 17건 모두 기대한 오류 코드로 거름 (`node spikes/interactive-components/harness.mjs`) |
| 4 | 가정값 구분 표시, 출처와 기준 시점 표시 | 확인 (개발 환경) | 가정값은 "가정값" 표시와 안내 문장, 모든 설명 아래에 자료와 기준 시점 |
| 5 | 강제 실패 시 대체 시각 요소, 실패 기록 | 확인 (개발 환경) | 틀린 수치 주입과 표시 오류 주입 모두에서 6건 전부 요약 카드로 바뀌고, 글자만 남은 것은 0건, 실패 12건이 기록됨 |
| 6 | 화면 크기 범위에서 잘림·겹침 없음 | 일부 확인 | 360×780 한 가지 크기에서 가로 넘침 없음. 다른 크기와 실기기는 미확인 |
| 7 | 조작하지 않아도 핵심을 알 수 있음 | 확인 (개발 환경) | 처음 열었을 때 기본 선택 상태의 결과가 보인다. 판단은 창업자 확인이 필요하다 |

**창업자 실기기 확인 (2026-11-15)**: "인터랙티브 시험해봤어. 인터랙티브 콘텐츠 자체는 괜찮아." 기준 1(실기기에서 2가지 이상 동작)은 이 말로 확인된 것으로 본다. 기준 2(스크롤과의 충돌, 한 손 조작)는 따로 언급이 없어 문제가 없었다는 뜻으로 받아들이되, 명시적 확인은 아니다. 창업자가 남긴 다음 질문: 이 품질이 Sonnet이나 GPT 경량 모델이 스펙을 만들었을 때도 나오는지는 돌려 봐야 안다. S5b와 핵심 가치 프로토타입의 모델 비교에서 다룬다.

주입한 오류 17건: 사실과 다른 수치, 참조 없는 수치, 없는 사실 ID, 모르는 유형, 조작 안내 누락, 출처 누락, 틀린 계산식 2종, 대조값 없는 계산, 범위 밖 기본값, 효과 없는 입력, 식 안의 근거 없는 숫자, 식에 코드 넣기, 식의 모르는 이름, 과정의 없는 사실 ID, 과정의 틀린 수치, 가정값 표시 없는 예시 금액.

## 9. 관찰한 한계

- **검증 하네스가 잡지 못하는 것**: 사실 목록 자체가 틀린 경우(스펙과 사실 목록이 함께 틀리면 통과한다. 사실 목록의 검증은 집필·검증 단계의 일이다). 계산식과 대조값이 같은 방식으로 함께 틀린 경우. 유형 선택이 설명 목적에 맞는지. 문장 설명의 사실 여부.
- 관계 유형(관계도)은 아직 만들지 않았다.
- 실기기 확인 전이다. 기준 1, 2는 통과로 보고하지 않는다.
- 화면 크기는 한 가지만 자동 점검했다.
- 이해에 도움이 되는지는 평가하지 않았다 (FR-D-14).
- 이 결과는 AC-MU-05의 합격이 아니다.
