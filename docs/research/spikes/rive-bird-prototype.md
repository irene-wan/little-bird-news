# Technical Spike S6 — Rive 새 프로토타입

| 항목 | 내용 |
|---|---|
| 문서 상태 | **Draft v0.3**. 2026-11-15 창업자 지시로 수행했다. 시험 페이지를 만들어 게시했고 맥북에서 동작을 확인했다. **폰에서의 확인(검증 기준 1~4)은 창업자가 해야 한다** (8장) |
| 검증하는 Gate | F-06 (Rive 초기 프로토타입) |
| 관련 결정 | D-008, D-026, D-031 (Confirmed) · D-017, D-022 (Pending) / PRD FR-E-01~03, FR-E-08~09, NFR-P-02~03, NFR-U-04 |
| 상위 문서 | `docs/architecture/technical-discovery.md` 6장 |
| 형태 | 격리된 실험 코드 (`spikes/rive-bird/` 제안) |

## 1. 목적

Rive로 실제 움직임과 터치 반응이 있는 새를 모바일 웹에서 구현할 수 있는지, 읽기 화면의 성능을 해치지 않는지 1~2일 규모로 확인한다 (D-031, FR-E-08). 이 기간은 초기 상호작용 검증 목표이며 애니메이션 완성을 보장하지 않는다 (B§9.6).

## 2. 범위

**포함**

- 제한된 애니메이션 상태로 네 순간(등장, 소식 전달, 터치 반응, 마무리)을 표현한다. 상태를 재사용해도 된다 (D-026)
- 시험용 읽기 화면: 긴 한국어 본문(가짜 내용)을 스크롤하는 모바일 웹 페이지에 새를 넣는다
- 터치 반응
- 움직임을 불러오지 못했을 때 읽기가 그대로 가능한지 (FR-E-09)
- (권장) 움직임을 줄이는 기기 설정에 대한 대응 (NFR-U-04)
- Rive 런타임과 에디터의 이용 조건 확인
- 애셋 제작에 든 시간과 난이도, 상태를 늘릴 때의 확장 가능성 기록

**제외**

- 새의 최종 디자인과 완성된 애니메이션
- 상황별 대사 (D-017에서 따로 정한다)
- 제품 코드로의 통합, 인터랙티브 컴포넌트와의 통합 화면 (S5a와 따로 진행하되, 같은 페이지에서의 공존은 두 Spike가 끝난 뒤 확인을 제안한다)
- Rive 최종 채택 결정. 부적합하다는 증거가 나오면 증거를 기록하고 창업자에게 올린다. 기술 변경은 창업자 승인이 필요하다 (D-031)

## 3. 방법

1. 애셋을 준비한다 (6장의 입력에 따른다).
2. 상태 기계의 입력을 네 순간과 터치에 대응시킨다.
3. 시험용 읽기 화면에 넣고, 화면 상태(진입, 전달, 읽는 중, 마무리)에 따라 상태를 바꾼다.
4. 애셋 로딩을 일부러 실패시켜 읽기가 가능한지 본다.
5. 창업자가 실기기에서 직접 확인한다. 개발 환경에서의 확인과 실기기 확인을 구분해 기록한다.

## 4. 검증 기준

| # | 기준 | 확인 주체 |
|---|---|---|
| 1 | 네 순간 모두에서 새가 실제로 움직인다 (정적 이미지가 아니다) | 실기기, 창업자 |
| 2 | 새를 터치하면 반응하고, 늦다고 느껴지지 않는다 | 실기기, 창업자 |
| 3 | 새가 본문을 가리지 않고, 읽는 동안 스스로 주의를 끄는 움직임을 일으키지 않는다 | 실기기, 창업자 |
| 4 | 새가 있을 때와 없을 때 스크롤이 체감상 다르지 않다 | 실기기, 창업자 |
| 5 | 애셋 로딩이 실패해도 본문을 끝까지 읽을 수 있고, 실패가 기록된다 | 강제 실패 시험 |
| 6 | 런타임과 애셋의 용량, 첫 표시까지 걸린 시간이 측정되어 기록되었다 | 측정값 |
| 7 | 애셋 제작 시간, 난이도, 막힌 지점이 기록되었다 | 기록 |

기준 1~4는 창업자의 실기기 확인 없이는 통과로 보고하지 않는다 (P-12).

## 5. 산출물

- 실기기에서 열 수 있는 시험용 페이지
- 검증 기준별 결과 (확인한 것과 확인하지 못한 것의 구분)
- 애셋 제작 기록, 상태 구성안
- D-017에 대한 선택지 정리 (Proposed)

## 6. 선행 조건과 창업자 입력

- **새 그림과 움직임 파일의 조달** (2026-11-14 엔지니어 선택, 창업자 위임에 따름): Rive는 미리 그려 둔 캐릭터 파일을 화면에서 움직여 주는 도구다. 그 파일은 Rive 에디터라는 그림 프로그램에서 사람이 그리고 움직임을 넣어 만든다. AI는 그 프로그램을 대신 다룰 수 없다. 그래서 프로토타입에는 Rive 커뮤니티에 공개된 기성 캐릭터 가운데 이용 조건이 확인되는 것을 골라 쓴다. 이것으로 "Rive가 폰에서 잘 움직이고 터치에 반응하는가"를 먼저 확인한다. 우리 새의 그림을 누가 그릴지는 그 뒤에 정한다 (D-017).
- 실기기: 갤럭시 S23의 모바일 브라우저 (2026-11-14 창업자 입력).

## 7. 규모

1~2일 (B§9.6, P-16). 애셋 준비에 걸리는 시간은 따로 기록한다.

## 8. 결과 (2026-11-15)

창업자가 2026-11-15에 착수를 지시했다 (Technical Design 초안 뒤에 이 브리프대로, 이용 조건이 확인된 기성 애셋으로 만들라는 지시). 코드는 `spikes/rive-bird/`에 있다.

**폰에서 여는 곳**: https://claude.ai/artifact/DJuge9UZ2Rkic1mXgSqqD1 (창업자 계정의 비공개 페이지). **이 주소에서 새가 실제로 뜨는지는 확인하지 못했다** (9장 첫 항목). 새 대신 멈춘 새 그림이 보이면 위쪽 "시험 도구"를 눌러 기록에 "막힘"이나 "실패"로 시작하는 줄이 있는지 봐 주면 된다. 그 경우의 다른 길: 맥북에서 `node spikes/rive-bird/build.mjs` 다음 `node spikes/rive-bird/serve.mjs --lan`을 실행하고, 같은 와이파이의 폰에서 `http://<맥북의 IP>:4174`를 연다.

**만든 것**

| 항목 | 내용 |
|---|---|
| 애셋 | Rive Marketplace의 "Bird" (만든 이 JcToon). 페이지에 표시된 이용 조건은 **CC BY** (출처 표시). https://rive.app/community/files/1750-3467-bird/ . 파일은 `spikes/rive-bird/assets/bird-jctoon.riv`, 142,374바이트. 화면 아래에 만든 이와 주소를 적었다 |
| 애셋에 든 것 | 움직임 3개(`Idle`, `Blink`, `Jump`), 상태 기계 1개(`State Machine 1`), 입력 1개(`Pressed`: 누르면 `Idle → Jump → Idle`) |

| 시험 도구 | 화면 위쪽 버튼. 새 있음 / 새 없음 / 움직임 줄이기 / 불러오기 실패 두 가지를 바꿔 볼 수 있고, 측정값과 기록이 보인다 |

**네 순간을 이 애셋으로 만든 방법** (상태 재사용, D-026)

| 순간 | 언제 | 구현 |
|---|---|---|
| 등장 | 도착 화면 | 웹 쪽에서 화면 밖에서 날아와 앉는 이동을 주고, 앉을 때 `Pressed`를 한 번 쏜다. 도착 화면에서는 `Idle`(숨쉬기, 눈 깜빡임)이 계속 돈다 |
| 전달 | 소식을 열 때 | 새가 말풍선("이 소식을 가져온 이유") 옆으로 오며 `Pressed`를 한 번 쏜다 |
| 터치 반응 | 새를 누를 때, 확인 문제에 답할 때 | `Pressed` |
| 마무리 | 마지막 소식 뒤 | `Pressed` 한 번, 그 뒤 `Idle` |
| (읽는 중) | 소식 화면 | 반응이 끝나면 그리기를 멈춘다. 말풍선이 화면 밖으로 나가면 새는 위쪽 띠의 작은 자리(44px)로 옮겨 가만히 있는다 |

## 9. 관찰한 한계

- **게시한 주소에서 새가 뜨는지 확인하지 못했다.** 비공개 페이지는 바깥 주소로 나가는 요청을 막는다. 그래서 움직임 도구의 본체(`rive.wasm`)를 페이지와 함께 올리고 그림 파일은 페이지 안에 넣었다. 그래도 그 페이지의 보안 규칙이 wasm 실행 자체를 막을 수 있고, 이 세션에서는 그 페이지를 열어 볼 수 없었다(로그인이 필요하다). 막히면 멈춘 새 그림이 나오고 기록에 남는다. 폰에서의 첫 확인이 이 항목의 확인이다.
- **폰에서 본 것이 하나도 없다.** 위의 "확인"은 모두 맥북의 크롬을 자동으로 조작해 얻은 것이다. 이 앱 안의 미리보기 창은 화면에 보이지 않을 때 움직임을 멈춰서 쓸 수 없었다.
- **이 애셋은 우리 새가 아니다.** 입력이 하나(`Pressed`)뿐이어서 네 순간이 모두 같은 "폴짝"이다. 날아오고 건네는 느낌은 웹 쪽의 이동으로 흉내 냈다. Technical Design 5.2절의 애셋 계약(입력 넷)은 시험하지 못했다.
- **애셋에 지울 수 없는 배경색이 있다.** 그림 파일의 대지가 청회색으로 칠해져 있어 새를 둥근 창 안에 넣었다. 우리 새는 배경이 투명해야 한다.
- **새가 대지의 4분의 1만 차지한다.** 잘라서 키워 보여 준다. 위쪽 띠의 작은 자리(44px)에서는 뛰어오를 때 머리 위가 조금 잘린다. 우리 새는 대지를 꽉 채워 그리고 자리 크기별 여백을 약속해야 한다.
- 몸통이 비트맵 그림이다. 크게 그렸을 때의 선명도는 폰에서 봐야 한다.
- **런타임이 예고한 변화**: 2.47.1은 "상태 기계 입력"과 "상태 바뀜 알림"을 앞으로 없앨 방식이라고 경고한다. 새 방식은 데이터 바인딩(그림 파일의 값에 이름을 붙여 바깥에서 바꾸는 방식)이다. 2021년에 만든 이 애셋은 옛 방식만 가진다. 우리 새의 애셋 계약은 새 방식으로 정해야 한다. 새 방식은 시험하지 않았다.
- 런타임의 용량이 작지 않다 (스크립트와 wasm을 합쳐 압축 전 1.3MB). 첫 화면이 그려진 뒤에 불러오게 했으므로 읽기를 막지는 않는다. 폰의 느린 통신망에서 새가 몇 초 뒤에 나타나는지는 재지 않았다.
- CC BY 외의 추가 조건이 Rive 이용 약관에 있는지는 읽지 않았다. 혼자 시험하는 용도를 넘어 쓰려면 확인해야 한다.
- Rive 에디터의 무료 요금제에서 파일을 내보낼 수 있는지는 자료마다 말이 달랐다 (공식 문서: 가능하되 시작 화면이 붙는다 / 다른 자료: 유료). 우리 새를 만들 때 확인해야 한다.
- 조작형 컴포넌트(S5a)와 같은 화면에 두는 것은 하지 않았다 (브리프의 제외 범위). 조작형이 들어갈 자리는 비워 두었다.
- 정서적으로 좋은지(귀여움, 전달받는 느낌)는 이 Spike가 보지 않는다. 기술 동작만 본다.

## 10. D-017에 대한 정리 (Proposed)

- Rive는 맥북의 크롬에서 요구한 동작(네 순간, 터치 반응, 읽는 중 정지, 실패 대체, 움직임 줄이기)을 모두 했다. 부적합하다는 증거는 없다. 폰 확인 전이므로 채택을 확정할 근거도 아직 아니다 (D-031).
- 우리 새의 그림 파일에 요구할 것: 투명 배경, 대지를 채우는 크기, 입력 넷(등장·전달·반응·마무리)과 가만히 있는 상태, 데이터 바인딩 방식. 이 약속을 지키면 파일만 갈아 끼운다.
- 누가 그릴지는 창업자가 정한다 (Technical Design 15.1절 D-054).
