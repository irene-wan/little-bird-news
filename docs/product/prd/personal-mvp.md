### 0.2 표기 규칙

- **근거 열**: `B§9.3` = Product Brief 9.3절, `P-04` = Product Principles 원칙, `D-007` = Decision Log 결정.
- **`검토 Q-nn`, `검토 G`, `검토 10`** (근거 열): 2026-11-14 창업자 검토 의견에서 정해진 방향. Q-01~07과 Q-18(Rive)은 9.1절에 정리했고, `검토 G`는 지원 기능 G에 대한 의견, `검토 10`은 추가 수정 의견, `검토 V`는 모든 소식에 시각 요소를 필수로 한 결정이다. Decision Log v1.1(2026-11-14)에 D-024~D-039로 등록되었다. 대응은 9.1절에 적었다.
- **`[가정 Q-nn]`**: 승인 문서에 답이 없어 이 초안이 임시로 둔 가정. 언제 어디서 정하는지는 9.2절과 9.3절에 나눠 적었다.
- **`[미결정 D-nnn]`**: Decision Log에 이미 올라 있는 미결정 사항. **`[미결정 T-nn]`**: 이 PRD를 쓰면서 새로 드러난 미결정 사항(T-04는 Decision Log D-034로 등록되었고, 나머지는 Decision Log에 없음). 둘 다 8장에 정리한다.
- **`[합격선 D-018]`**: 정량 기준은 평가를 시작하기 전에 Evaluation Spec에서 확정한다. 이 문서는 숫자를 정하지 않는다.
- 요구사항 문장의 "~해야 한다"는 MVP 필수다. 필수가 아닌 것은 "권장"으로 따로 적었다.
- **Technical Discovery**: 기술 설계에 앞서 기술 후보를 탐색하고 검증하는 단계 (Brief 14장의 Technical Spike 포함). 컴포넌트 종류나 구현 기술 같은 선택은 여기서 정한다.
- **Evaluation Spec**: 평가 기간, 합격선, 표본 확보 방법을 평가 전에 고정하는 문서 (D-018).
- **편집 정책**: 정치 공방성 콘텐츠와 중요한 정책·사회 이슈의 경계 등을 정하는 별도 문서 (P-09).
- 이 문서는 **무엇을 만족해야 하는지**만 적는다. **어떻게 구현하는지**는 적지 않으며, 구현 방식이 필요한 곳은 8장으로 넘겼다.

### 0.3 용어

| 용어 | 뜻 |
|---|---|
| 소식 | 사용자에게 전달되는 뉴스 콘텐츠 한 편 (D-001). 중복 보도를 정리해 사건으로 묶고, 그 사건들을 평가해 선정한 것을 사용자에게 맞게 집필한 최종 결과물이다. 소식 한 편은 선정된 사건 하나를 다룬다 (검토 Q-19) |
| 보도 | 공급원에서 받은 개별 기사 |
| 사건 | 같은 일을 다룬 여러 보도를 하나로 묶은 단위 |
| 후보 사건 | 추천 평가 대상이 된 사건 |
| 연결고리 | 프로필의 특정 항목과 사건의 특정 사실 사이에 있는, 근거를 댈 수 있는 관계 |
| 추천 이유 | 연결고리를 사용자가 이해할 수 있게 풀어 쓴 설명 |
| 오늘의 소식 | 하루에 전달되는 소식 묶음. 수량은 `[미결정 D-019]` |
| 인터랙티브 설명 | 사용자가 값이나 선택지를 바꾸면 결과가 달라지는 조작형 설명 요소 |
| 주제 영역 | 뉴스가 다루는 분야. 목록은 Evaluation Spec에서 확정한다. 인터랙티브 표현 유형과 구분해 관리한다 |
| 인터랙티브 표현 유형 | 설명에 쓰는 조작형 표현의 종류. 초기 검토 대상은 관계, 과정, 비교, 시뮬레이션이다 |
| 고정 기술 테스트 사례 | 추천 결과와 무관하게 인터랙티브 기능을 반복 확인하려고 미리 정해 둔 사례 묶음 |
| 독립 뉴스 표본 | 추천 시스템을 거치지 않고 따로 확보한 뉴스 표본. 수집 단계에서 놓친 사건을 점검하는 데 쓴다 |
| 발견형 소식 | 기존 관심사 밖이지만 근거 있는 연결이 있어 세계를 넓혀 주는 소식 (P-08) |
| 발행 보류 | 검증을 통과하지 못해 사용자에게 전달하지 않는 것 |
| 결정 기록 | 후보 사건별 평가 결과와 선정·제외 이유를 남긴 기록 |
| 평가자 | 소식과 경험을 평가하는 역할. 최초 MVP에서는 창업자 본인이 사용자이자 평가자다. 평가자의 체험 평가는 모델의 자체 평가와 구분해 기록한다 |

## 1. 제품 요약과 바꾸지 않는 기준

### 1.1 MVP의 목적

창업자 본인 한 사람에게 세 가지 핵심 가치가 실제로 전달되는지 확인하는 개인용 제품이다 (B§9.1, D-002).

| 핵심 가치 | 한 줄 정의 | 근거 |
|---|---|---|
| Personal Relevance | 나와 관련된 소식을 근거 있게 발견한다 | B§6A, P-01 |
| Meaningful Understanding | 깊은 이해와 흥미, 지적 만족을 얻는다 | B§6B, P-03 |
| Emotional Experience | 새와 함께하는 경험에서 즐거움과 정서적 만족을 느낀다 | B§6C, P-06 |

### 1.2 합격 원칙

- 세 가치 중 하나라도 미달하면 MVP 전체가 미완료다 (D-003).
- 이 단계의 합격은 개인적 사용 경험의 합격이다. 시장 수요나 다른 사용자에 대한 검증이 아니다 (B§3, P-13).
- AI가 "완료했다"고 보고한 것만으로는 어떤 기능도 합격하지 않는다 (P-12).

### 1.3 축소하지 않는 세 가지

아래 세 항목은 일정이나 난이도를 이유로 줄이지 않는다. "조정 가능한 것" 열은 Product Principles 5장(변경 관리 원칙)이 허용하는 범위다.

| 항목 | 반드시 유지하는 것 | 축소로 간주하는 것 | 조정 가능한 것 |
|---|---|---|---|
| 개인화 추천 품질 | 사건 정리, 프로필과 사건의 연결고리 도출, 5개 기준 평가, 근거와 대조한 추천 이유, 선정·제외 기록, 원인 추적, 반복 개선 (B§9.3, D-005, P-14) | 키워드 일치만으로 추천을 끝내는 것. 추천 이유 없이 결과만 내놓는 것. 기록·추적을 빼는 것. 인터랙티브를 넣기 쉬운 사건 쪽으로 추천을 왜곡하는 것 | 알고리즘과 단계 구성, 사용하는 모델, 후보 수집 범위 |
| AI 인터랙티브 지식 콘텐츠 | AI가 설명 목적에 맞는 표현을 고르고, 사용자가 실제로 조작하며, 사실·숫자·논리가 검증된 인터랙티브 설명. 서로 다른 최소 2가지 인터랙티브 방식이 실제로 동작. 전달되는 모든 소식은 글자만으로 이루어지지 않으며, 인터랙티브 설명을 기본으로 하고 그것이 적합하지 않거나 실패하면 시각 콘텐츠나 권리가 확인된 자료사진을 넣는다 (B§9.5, D-007, P-15, 검토 Q-02, 검토 V) | 글자만 있는 소식을 전달하는 것. 정적 이미지를 인터랙티브 설명 실적으로 치는 것. 한 가지 방식만 동작. 고정 기술 테스트 사례에서만 확인하고 실제 소식에서의 사용 결과를 보지 않는 것. 대체 시각 요소에 기대어 인터랙티브 설명을 사실상 만들지 않는 것 | 컴포넌트 종류와 구현 기술(Technical Discovery에서 결정), 인터랙티브가 적합하지 않은 소식에서 대체 시각 요소의 종류 |
| 최소 감성적 새 경험 | 새가 등장·소식 전달·터치 반응·마무리의 네 순간 모두에 실제 움직임으로 참여 (B§9.6, D-008, P-16, 검토 Q-03) | 정적 이미지뿐인 새. 터치 반응 없음. 네 순간 중 일부에만 참여 | 애셋의 정교함, 애니메이션 상태의 수(제한된 상태를 재사용해도 됨), 최종 구현 기술(Rive가 우선 기술이며, 부적합하다는 증거가 있으면 창업자 승인을 받아 변경. 검토 Q-18) |

## 2. 사용자 흐름

### 2.1 흐름 한눈에 보기

```
[F0 최초 설정]  접근 확인 → 프로필 최소 항목 입력 → 저장 → 첫 소식 준비 안내
                                   │
                                   ▼
[F1 하루 읽기]  진입 → 새 등장 → 소식 전달 → 읽기(+조작) → 소식 완료
                         ↑                                      │
                         └────── 남은 소식이 있으면 반복 ◄──────┘
                                                                │ 마지막 소식
                                                                ▼
                                        새와 마무리 → 종결 상태 (추가 피드 없음)

[F2 프로필 관리]  언제든: 열람 → 추가 · 수정 · 삭제 → 다음 소식 준비부터 반영
[F3 평가·피드백]  읽은 뒤(읽기와 분리): 간단한 소식별·세션 평가 · 오류 신고
                 개발자용 도구: 기록 확인 · 누락 점검 · 원인 추적 · 재실행
[F4 예외]        소식 미준비 · 소식 수 감소 · 소식 없는 날 · 며칠 만의 복귀 · 화면 요소 실패
```

### 2.2 F0 — 최초 설정 (1회)

| # | 사용자 | 제품 | 관련 요구사항 |
|---|---|---|---|
| 1 | 모바일에서 서비스를 처음 연다 | 본인만 접근할 수 있는지 확인한다 | NFR-S-01 |
| 2 | 프로필 입력 화면에서 최소 항목을 직접 입력한다 | 필수는 소수 항목뿐임을 보여 주고, 나머지는 나중에 추가할 수 있다고 안내한다 | FR-A-01, FR-A-02 |
| 3 | 원하면 서술형 정보를 더 적는다 | 압박 없이 받는다. 민감한 정보는 정해진 범위에서만 받는다 | FR-A-04, FR-A-09, FR-A-10 |
| 4 | 저장한다 | 저장 결과를 확인시키고, 첫 소식이 언제부터 준비되는지 알려 준다 | FR-A-07, FR-F-09 |

대화형 온보딩은 이 흐름에 없다 (B§7.1a, D-004). 새가 F0에 등장하는지는 요구사항이 아니다.

### 2.3 F1 — 하루 읽기 (핵심 흐름)

| # | 단계 | 사용자 | 제품 | 새 | 관련 요구사항 |
|---|---|---|---|---|---|
| 1 | 진입 | 서비스를 연다 | 본인 접근을 확인하고 오늘의 소식 준비 상태를 확인한다 | — | NFR-S-01, FR-F-09 |
| 2 | 등장 | 화면을 본다 | 오늘 전달할 소식이 몇 편인지 알려 준다 | 등장하는 움직임으로 소식을 가져왔음을 알린다 | FR-E-01, FR-F-02 |
| 3 | 전달 | 소식을 받는다 | 소식 한 편을 연다 | 소식을 건네는 움직임 | FR-E-01 |
| 4 | 읽기 | 읽는다 | 핵심 사실, 나와의 관계(추천 이유), 배경지식, 개념 설명, 출처와 시점을 보여 준다 | 읽기를 방해하지 않는다. 터치하면 반응한다 | FR-C-03, FR-E-02, FR-E-03 |
| 5 | 조작 | 인터랙티브 설명에서 값이나 선택지를 바꿔 본다. 인터랙티브 설명이 없는 소식에서는 대체 시각 요소(시각 콘텐츠나 자료사진)를 본다 | 바뀐 값에 맞는 결과를 보여 준다 | — | FR-D-01, FR-D-03, FR-D-07 |
| 6 | 소식 완료 | 다음으로 넘어간다 | 진행 위치를 갱신한다 (예: 2/N) | (권장) 가볍게 반응한다. 기존 애니메이션 상태를 재사용해도 된다 | FR-F-02 |
| 7 | 반복 | 남은 소식을 3~6단계로 읽는다 | — | — | — |
| 8 | 마무리 | 마지막 소식을 마친다 | 추가 소식이나 추천 없이 종결 상태로 바꾼다 | 마무리 움직임, 짧은 상황별 대사, 터치 반응. 자유 대화는 없다 | FR-F-03, FR-F-04, FR-E-01, FR-E-10 |
| 9 | 종료 | 서비스를 닫거나 새와 잠시 논다 | 종결 상태를 유지한다 | 터치에 반응한다 | FR-F-10 |

- 소식 안에서 구성 요소를 어떤 순서와 모양으로 배치할지는 UX 설계에서 정한다. 이 표는 포함되어야 하는 요소만 고정한다.
- 모든 소식에는 글자 말고도 볼 것이 있다. 인터랙티브 설명이 기본이고, 그것이 적합하지 않거나 실패한 소식에는 시각 콘텐츠나 자료사진이 들어간다 (FR-D-01, 검토 V).
- 평가(F3)는 읽기 흐름과 분리된다. 읽는 도중에 평가를 요구하지 않는다 (검토 Q-07).
- 본문은 프리미엄 지식 콘텐츠로 읽힌다. 새는 전달자이자 설명을 돕는 캐릭터로 곁에 있으며, 본문 전체가 새의 대사는 아니다 (검토 Q-03).

### 2.4 F2 — 프로필 관리

| # | 사용자 | 제품 | 관련 요구사항 |
|---|---|---|---|
| 1 | 프로필 화면을 연다 | 저장된 모든 정보를 직접 입력과 AI 추론으로 구분해 보여 준다 | FR-A-05, FR-A-08 |
| 2 | 항목을 추가하거나 더 구체적으로 고친다 | 저장하고, 다음 소식 준비부터 반영된다고 알린다 | FR-A-03, FR-A-07 |
| 3 | 항목을 삭제한다 (항목 단위 또는 전체) | 삭제하고, 이후 추천과 집필에 쓰지 않는다 | FR-A-06, FR-A-07 |

### 2.5 F3 — 평가와 피드백

평가는 두 갈래다. 모바일에는 간단한 평가와 피드백만 두고, 기록 확인과 원인 추적은 개발자용 도구로 한다. 내부 추적 기능을 모두 모바일 화면으로 만들지 않는다 (검토 G).

**사용자용 (모바일, 읽기를 마친 뒤)**

| # | 사용자 | 제품 | 관련 요구사항 |
|---|---|---|---|
| 1 | 원하면 소식별로 간단히 평가한다 (관련성, 추천 이유의 정확성, 이해, 흥미, 인터랙티브 유용성) | 평가를 소식과 연결해 저장한다 | FR-G-01 |
| 2 | 원하면 세션 전체를 간단히 평가한다 (새 경험, 성취감·휴식감, 피로) | 저장한다 | FR-G-02 |
| 3 | 사실 오류, 잘못된 연결, 화면 오류를 신고한다 | 해당 소식의 근거와 기록에 연결해 저장한다 | FR-G-03 |

**개발자용 (모바일 화면 불필요)**

| # | 평가자 | 제품 | 관련 요구사항 |
|---|---|---|---|
| 4 | 그날의 후보와 제외 목록을 확인해 "왔어야 했던 소식"을 표시한다 | 누락 사례로 기록한다 | FR-B-13, FR-G-04 |
| 5 | 독립 뉴스 표본과 대조해 수집 단계에서 놓친 사건을 점검한다 | 수집 누락인지 제외인지 구분해 기록한다 | FR-G-12 |
| 6 | 잘못된 추천이나 누락의 원인을 확인하고, 같은 사례를 다시 실행해 본다 | 어느 단계에서 생긴 문제인지 보여 준다 | FR-B-14, FR-G-05, FR-G-13 |

### 2.6 F4 — 예외 흐름

| 상황 | 사용자가 겪는 것 | 근거 |
|---|---|---|
| 오늘의 소식이 아직 준비되지 않음 | 준비 중임을 알리는 안내. 오류 화면이나 빈 화면이 아니다 | FR-F-09 |

| 며칠 만에 다시 접속 | 하루 읽기에서는 오늘의 소식만 받는다. 미읽음 표시, 끊긴 연속 기록, 재촉이 없다. 읽지 못한 날의 소식은 원할 때 지난 소식에서 볼 수 있다 (FR-F-12) | P-05, B§6C, 검토 Q-09 |
| 읽다가 나갔다가 같은 날 돌아옴 | 읽던 곳에서 이어서 읽는다 | FR-F-06 |

| 새 움직임이 불러와지지 않음 | 읽기는 그대로 가능하다. 실패는 기록된다 | FR-E-09 |
| 네트워크가 끊김 | 무엇이 안 되는지 알려 주고, 복구되면 이어 간다 | NFR-A-03 |

### 2.7 소식이 준비되는 과정 (사용자에게 보이지 않는 흐름)

제품이 단계마다 보장해야 하는 결과를 적었다. 단계를 어떻게 구현하고 자동화할지는 기술 설계에서 정한다. 다만 선정과 집필이 서로 다른 평가 단계여야 한다는 점은 승인된 제품 요구다 (B§7.3).

| 단계 | 제품이 보장하는 결과 | 근거 |
|---|---|---|
| 수집 | 이용 권리가 확인된 보도만 들어오고, 출처와 시간이 보존된다 | B§9.3, P-11 |
| 사건 정리 | 같은 사건의 중복 보도가 하나로 묶인다 | B§7.2 |
| 후보 평가 | 사건마다 프로필과의 연결고리와 5개 기준 평가가 근거와 함께 남는다 | B§9.3 |
| 선정 | 오늘의 소식이 정해지고, 모든 후보의 선정·제외 이유가 기록된다 | B§9.3 |
| 사실 확인과 집필 | 원문 근거와 대조된 사실만으로, 사용자에게 맞는 수준으로 쓰인다 | B§9.4 |
| 인터랙티브 구성 | 선정된 소식에 설명 목적에 맞는 조작형 설명이 붙는다. 적합하지 않거나 실패하면 시각 콘텐츠나 권리가 확인된 자료사진이 붙는다. 글자만 있는 소식은 나가지 않는다 | B§9.5, 검토 V |
| 발행 전 검증 | 문장, 숫자, 추천 이유, 시각화가 각각 검증된다 | P-04 |
| 발행 또는 보류 | 통과한 소식만 전달되고, 보류된 소식은 사유가 남는다 | D-015, D-023 |

| FR-B-22 | MVP에서 다루는 뉴스는 국내로 한정한다. 해외로 넓히는 것은 이후 단계의 일이다. "국내"의 정확한 경계(국내 매체가 보도한 해외 사건의 포함 여부 등)는 공급원 조사와 함께 정한다 `[미결정 D-012]` | 검토 Q-14 |

### 3.3 CORE C — 개인화 프리미엄 집필

**목적**: 확정된 사건을, 이 사용자가 다른 검색 없이 이해하고 기억에 남길 수 있는 프리미엄 지식 콘텐츠로 쓴다.

| ID | 요구사항 | 근거 |
|---|---|---|
| FR-C-01 | 선정과 집필은 별도의 평가 단계여야 한다. 글이 잘 쓰였다는 이유로 관련성이 낮거나 사실이 틀린 소식이 통과해서는 안 된다 | B§7.3 |
| FR-C-02 | 소식의 모든 사실 주장, 숫자, 인용은 원문 근거와 대조되어야 한다. 근거를 댈 수 없는 내용은 싣지 않는다 | B§9.4, P-04 |
| FR-C-03 | 소식은 핵심 사실, 나와의 관계(추천 이유), 배경지식, 개념과 용어 설명을 포함해야 한다 | B§7.4 |

| FR-C-06 | 확인된 사실과 해석·추론은 독자가 구분할 수 있게 표시되어야 한다 | B§9.4, P-04 |
| FR-C-07 | 사건의 시점과 출처가 표시되어야 하며, 권리가 허용하는 범위에서 원문으로 갈 수 있어야 한다 | B§9.4, P-04, P-11 |
| FR-C-08 | 불확실한 내용과 보도 간 차이는 숨기지 않고 밝힌다 | P-04 |
| FR-C-09 | 단순 요약에 그치지 않는다. 사건의 의미와 맥락을 설명하고, 읽고 난 뒤 남는 알맹이를 독자가 알아볼 수 있게 편집한다 | B§9.4, P-03, P-07 |

| FR-C-11 | 오늘의 소식 전체를 10분 이내에 마칠 수 있는 분량을 목표로 한다 `[가정 Q-13]` | B§5 |

### 3.4 CORE D — AI 인터랙티브 지식 콘텐츠

**목적**: 글만으로는 잡기 어려운 관계, 과정, 비교, 수치를 사용자가 직접 조작하며 이해하게 한다. 최초 MVP의 필수 요소다 (D-007, P-15).

| ID | 요구사항 | 근거 |
|---|---|---|
| FR-D-01 | 사용자에게 전달되는 모든 소식은 글자만으로 이루어져서는 안 된다. 선정된 소식에는 AI 인터랙티브 설명을 넣는다. 조작형 인터랙티브 설명이 그 소식에 적합하지 않거나 실패한 경우에는 글자만 내보내지 않고, 내용을 간단히 요약·설명하는 시각 콘텐츠(도식, 인포그래픽 등)나 이용 권리가 확인된 관련 뉴스 자료사진을 반드시 넣는다. 적합 여부의 판단과 이유, 어떤 요소가 들어갔는지를 기록한다 인터랙션이 어색한 소식에 조작형 설명을 억지로 넣지는 않되(B§9.5), 그런 소식에도 다른 시각 콘텐츠는 반드시 들어간다. 시각 자료가 불필요한 소식은 없다고 본다 | B§7.4, B§9.5, D-007, 검토 V |
| FR-D-02 | AI는 설명 목적에 맞는 인터랙티브 표현 유형을 고르고, 고른 이유를 기록한다. 초기에는 관계, 과정, 비교, 시뮬레이션(조작형 예시) 가운데 적합한 유형을 검토한다. MVP에서는 서로 다른 최소 2가지 인터랙티브 방식이 실제로 동작해야 한다. 구체적인 컴포넌트 종류는 Technical Discovery에서 정한다 `[미결정 D-016]` | B§9.5, 검토 Q-02 |
| FR-D-03 | 사용자가 값이나 선택지를 바꾸면 결과가 달라져야 한다. 움직이지 않는 그림은 인터랙티브 설명으로 인정하지 않는다 | B§9.5, P-15 |
| FR-D-04 | 인터랙티브 설명에 나오는 사실, 숫자, 관계, 논리는 출처와 일치하는지 검사되어야 한다. 조작에 따라 계산되는 결과도 검사 대상이다 | B§9.5, P-04 |
| FR-D-05 | 설명을 위해 넣은 가정값이나 예시값은 실제 보도된 수치와 구분되어 표시되어야 한다 | P-04 |
| FR-D-06 | 뉴스의 주제 영역과 인터랙티브 표현 유형을 구분해 관리한다. 인터랙티브 설명이 쓰인 소식마다 두 가지가 각각 기록되어, 어떤 주제 영역에서 어떤 표현 유형이 동작했는지 볼 수 있어야 한다. 여러 주제 영역에 걸친 합격 기준은 Evaluation Spec에서 정한다 `[합격선 D-018]` | B§9.5, B§9.9, 검토 Q-02 |
| FR-D-07 | 모바일 터치로 조작할 수 있어야 한다. 화면 스크롤과 조작이 서로 방해하지 않아야 한다 | B§9.7, D-016 |
| FR-D-08 | 표시나 검증에 실패한 인터랙티브 설명은 사용자에게 내보내지 않는다. 깨진 화면을 보이지 않고, 대체 시각 요소(시각 콘텐츠나 권리가 확인된 자료사진)를 넣어 전달한다. 글자만 남긴 채 내보내지 않는다. 실패는 기록하고 평가에서 인터랙티브 실패로 집계한다 | P-15, B§9.8, 검토 V |
| FR-D-09 | 인터랙티브 설명은 본문의 해당 설명 맥락 안에 놓이고, 무엇을 바꿔 보면 무엇을 알 수 있는지 안내한다 | P-07 |
| FR-D-10 | 사용자가 조작하지 않아도 소식의 핵심은 이해할 수 있어야 한다 | B§9.5 |
| FR-D-11 | 인터랙티브 설명에 쓰인 데이터의 출처와 기준 시점이 표시되어야 한다 | P-04 |
| FR-D-12 | AI가 구성한 인터랙티브 설명은 사용자에게 보이기 전에 표시, 조작, 내용(사실·수치·논리)을 검증할 수 있어야 하며, 검증되지 않은 것은 화면에 나오지 않는다. 이를 어떤 방식으로 구현할지는 Technical Discovery에서 정한다 `[미결정 D-016]` | B§9.5, P-15, 검토 10 |
| FR-D-13 | 자연 추천된 실제 소식에서의 사용 결과와 별도의 고정 기술 테스트 사례에서의 결과를 구분해 검증하고 따로 기록한다. 고정 기술 테스트 사례는 추천 결과와 무관하게 인터랙티브 기능을 반복 확인하기 위한 것이다 | D-007, P-12, 검토 Q-01 |
| FR-D-14 | 인터랙티브 설명이 기술적으로 동작하는지와 실제로 사용자의 이해에 도움이 되는지를 따로 평가한다. 한쪽의 결과로 다른 쪽을 대신하지 않는다 | P-12, P-15, 검토 Q-01 |
| FR-D-15 | 대체 시각 요소는 인터랙티브 설명의 실적으로 치지 않는다(FR-D-03). 소식마다 들어간 요소가 인터랙티브 설명인지, 시각 콘텐츠인지, 자료사진인지 구분해 기록하고, 인터랙티브 설명이 들어간 비율을 볼 수 있어야 한다. 비율에 대한 기준은 `[합격선 D-018]` | D-007, P-12, 검토 V |
| FR-D-16 | 대체로 넣는 시각 콘텐츠도 사실, 숫자, 관계가 출처와 일치하는지 검사하고 출처와 기준 시점을 표시한다. 자료사진은 해당 사건과 실제로 관련된 것이어야 하며 출처를 표시한다 | P-04, P-11, 검토 V |
| FR-D-17 | 어떤 소식이든 표나 도식 같은 시각 자료로 설명할 수 있다고 본다. "시각 요소를 넣을 수 없는 소식"이라는 분류는 두지 않는다. 시각 요소를 만들지 못했다면 소식의 성질이 아니라 제품의 결함으로 기록하고 고친다. 이 경우에도 글자만 있는 소식을 내보내지 않는다 | 검토 V |

### 3.5 CORE E — 최소 감성적 새 경험

**목적**: 소식이 "나를 아끼는 전달자가 정성껏 가져온 것"으로 느껴지게 한다. 새는 마스코트가 아니라 경험의 전달자다 (P-06).

| ID | 요구사항 | 근거 |
|---|---|---|
| FR-E-01 | 새는 등장, 소식 전달, 사용자 터치 반응, 마무리의 네 순간 모두에 실제 움직임으로 참여해야 한다. 정적인 이미지만으로는 충족되지 않는다. 네 가지 별도의 고급 애니메이션을 요구하는 것은 아니며, 제한된 애니메이션 상태를 재사용해도 된다 | B§9.6, D-008, P-16, 검토 Q-03 |
| FR-E-02 | 새를 터치하면 간단한 반응이 일어나야 하며, 반응이 늦다고 느껴지지 않아야 한다 | B§9.6 |
| FR-E-03 | 새는 읽기를 방해하지 않아야 한다. 본문을 가리지 않고, 읽는 동안 주의를 빼앗는 움직임을 스스로 일으키지 않는다 | B§9.6, P-07 |
| FR-E-04 | 새는 소식의 전달자이자 설명을 도와주는 캐릭터다. 모든 본문을 새의 대사로 쓸 필요는 없으며, 본문은 프리미엄 지식 콘텐츠로 유지한다 (FR-C-16). 새가 설명을 돕는 구체적인 형태는 UX 설계에서 정한다 | B§6C, P-06, 검토 Q-03 |
| FR-E-05 | 새는 출석, 연속 기록, 못 읽은 날에 대한 질책 등 압박이나 죄책감을 주는 표현과 행동을 하지 않는다 | P-05 |
| FR-E-06 | 새가 실제 의식이나 감정을 가진 존재라고 오해하게 만드는 표현을 쓰지 않는다 | P-06 |
| FR-E-07 | 새에 대한 애착을 개인정보 제공 압박에 이용하지 않는다 | P-10 |
| FR-E-08 | 필수 조건은 실제 움직임과 터치 반응이 있는 정서적 새 경험이다. Rive를 최초 구현의 우선 기술로 유지하고, Rive를 이용한 1~2일 규모의 작은 프로토타입을 먼저 검증한 뒤 그 결과에 따라 최종 기술을 확정한다. 이 기간은 초기 상호작용 검증 목표이며 애니메이션 완성을 보장하지 않는다. Rive가 부적합하다는 증거가 있으면 기술을 바꿀 수 있으나 창업자 승인을 받는다. 기술이 바뀌어도 FR-E-01~03은 그대로 적용된다 `[미결정 D-017]` | B§9.6, D-008, P-16, 검토 Q-18 |
| FR-E-09 | 새의 움직임을 불러오지 못해도 소식 읽기는 가능해야 하며, 실패는 기록된다 | P-17 |
| FR-E-10 | 마무리는 새의 짧은 상황별 대사, 움직임, 터치 반응으로 이루어진다. MVP에서 새와의 자유 대화는 제외한다. 장기적인 대화형 캐릭터 비전은 유지한다 | B§7.5, B§9.6, 검토 Q-04 |
| FR-E-11 | 새는 상황(등장, 소식 전달, 마무리, 전할 소식이 없는 날 등)에 맞는 짧은 대사를 쓸 수 있다. 대사는 FR-E-05~07을 지키고 읽기를 방해하지 않는다. 대사의 범위와 작성 방식은 `[미결정 D-017]` | P-06, 검토 Q-04 |

### 3.6 CORE F — 모바일 읽기와 마무리

**목적**: 정해진 소식만 읽고 분명하게 끝난다. 읽은 뒤 피로보다 만족이 남는다.

| ID | 요구사항 | 근거 |
|---|---|---|
| FR-F-01 | 모바일에서 오늘의 소식을 읽을 수 있어야 한다. 실행 형태는 `[미결정 D-022]` | B§9.7, D-022 |
| FR-F-02 | 오늘의 소식이 모두 몇 편이고 지금 몇 번째인지 알 수 있어야 한다 | B§6C, P-02 |
| FR-F-03 | 무한 피드, "더 보기", 관련 기사 추천 등 정해진 소식 밖으로 이어지는 요소가 없어야 한다 | B§9.7, P-02, D-009 |

### 3.7 지원 기능 G — 평가, 피드백, 추적

승인 문서의 CORE 목록(A~F)에는 없던 기능 묶음이며, 2026-11-14 검토에서 유지가 승인되었다 (검토 G). 세 가치의 검증(B§9.9, B§10)과 독립 평가 원칙(P-12)을 위한 것이다.

**범위 원칙** (검토 G)

- 개인용 MVP에 맞는 최소 범위로 만든다. 별도의 대규모 운영 대시보드를 만들지 않는다.
- 사용자에게 필요한 간단한 평가·피드백(G-1)과 개발자용 로그·평가 도구(G-2)를 구분한다.
- 내부 추적 기능을 모두 모바일 화면으로 만들 필요는 없다. G-2는 기록을 확인하고 다시 실행해 볼 수 있으면 형태를 가리지 않는다 `[미결정 T-05]`.

## 6. 세 가지 핵심 가치의 인수 조건

### 6.1 공통 규칙

| ID | 규칙 | 근거 |
|---|---|---|
| AC-0-01 | 세 가치가 모두 합격해야 MVP가 합격한다. 하나라도 미달이면 전체 미완료다 | D-003, B§9.1 |
| AC-0-02 | 평가는 서로 다른 날짜와 서로 다른 주제 영역에 걸쳐 반복한다. 기간과 횟수는 `[합격선 D-018]` | B§9.9, 검토 Q-02 |
| AC-0-03 | 정량 합격선은 평가를 시작하기 전에 Evaluation Spec에 적고, 이후 유리하게 고치지 않는다 | D-018 |
| AC-0-04 | 모델 자체의 평가와 창업자의 체험 평가를 구분해 기록한다. 모델의 자체 평가나 완료 보고는 합격 근거가 아니다 | P-12, 검토 Q-07 |
| AC-0-05 | 필수 품질(출처 확인, 기본 보안, 오류 처리, 데이터 보호, 품질 검증)이 지켜지지 않으면 가치별 점수와 관계없이 합격하지 않는다 | B§9.8, P-17 |
| AC-0-06 | 평가는 읽기 경험과 분리해 진행하며, 평가 때문에 읽기 경험이 방해받지 않는다 | P-05, 검토 Q-07 |
| AC-0-07 | 편향을 줄이기 위해 동일 사례의 재실행, 원문 근거 대조, 비교 기준선을 평가에 쓴다 | P-12, 검토 Q-07 |

각 가치의 인수 조건은 세 층으로 나뉜다.

- **구현 조건**: 기능이 요구대로 동작하는지 예/아니오로 확인한다.
- **체험 조건**: 반복 사용에서 측정한다. 지표는 B§10에서 가져왔고, 측정 방법은 제안이며, 합격선은 비워 두었다.
- **차단 조건**: 한 번이라도 일어나면 해당 가치를 합격시키지 않는 경우다. 허용 한도는 `[합격선 D-018]`에서 확정한다.

**구현 조건 — 인터랙티브 설명**

인터랙티브 설명은 두 갈래로 검증하고 결과를 따로 기록한다 (검토 Q-01).

| 갈래 | 무엇으로 검증하는가 | 무엇을 확인하는가 |
|---|---|---|
| 자연 추천 소식 | 실제로 추천되어 전달된 소식. 인터랙티브를 위해 추천을 바꾸지 않는다 | 실제 사용에서 필요성 판단이 맞았는지, 동작했는지, 이해에 도움이 됐는지 |
| 고정 기술 테스트 사례 | 추천 결과와 무관하게 미리 정해 둔 사례 묶음 | 인터랙티브 기능이 기술적으로 동작하는지 (반복 확인) |

기술적으로 동작하는 것과 이해에 도움이 되는 것은 따로 평가한다. 기술 동작은 아래 구현 조건으로, 이해 기여는 체험 조건으로 본다. 두 갈래의 결과를 합격 판정에 어떻게 반영할지, 자연 추천에서 인터랙티브 사례가 적을 때 어떻게 할지는 Evaluation Spec에서 정한다.

## 9. 검토로 정해진 방향과 남은 질문

v0.1의 질문 19개를 세 묶음으로 나눴다. **승인 전에 필요했던 9.2절의 네 건은 2026-11-14 답변으로 모두 정해졌고, 승인 전에 남은 질문은 없다.** 9.3절의 항목은 승인 뒤 해당 문서에서 정하며, 그때까지는 적어 둔 작업 가정으로 진행한다. 19개가 모두 풀려야 승인할 수 있는 것이 아니다.
