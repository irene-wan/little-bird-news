# Technical Design — 개인화 뉴스 서비스 · Personal Core Experience MVP

| 항목 | 내용 |
|---|---|
| 문서 상태 | **Draft v0.1**. 창업자 승인 전이다. 개발 기준으로 쓰지 않는다. 창업자가 승인하면 그때 아키텍처가 확정된다 (D-043) |
| 기준 문서 | MVP PRD v1.1 · Product Brief v1.0 · Product Principles v1.1 · Decision Log v1.3 · Assumption Register v1.0 |
| 입력 | `technical-discovery.md` 0절, `docs/research/spikes/` 의 Spike 기록, 목표 시안 (`docs/research/references/target-edition-mockup.html`) |
| 다루는 범위 | 소식 준비 과정, 화면 틀과 표현 시트, 읽기 화면과 새, 저장과 재실행, 배치와 도구, 프로필과 개인정보, 미결정 항목에 대한 제안 |

**이 문서의 모든 기술 선택은 Proposed다.** Decision Log는 고치지 않았다. 변경안은 15장에 모았다.

표기는 Technical Discovery와 같다 (`B§9.3`, `P-04`, `D-007`, `F-01`, `FR-/NFR-/AC-/T-/Q-`). 추가로 다음 두 가지를 쓴다.

- **[확인]** 실험에서 실제로 본 것. 몇 번 봤는지 함께 적는다.
- **[미확인]** 아직 해 보지 않은 것. 이 표시가 붙은 설계는 해 본 뒤에 바뀔 수 있다.

## 0. 한눈에

1. **품질은 화면 틀에서, 사실은 사실 목록에서, 비용은 앞 단계에서 정해진다.** 그래서 틀은 한 번 잘 만들어 고정하고, 경량 모델은 매일 짧은 빈칸만 채우고, 채운 것은 전부 코드와 다른 모델이 사실 목록에 대조한다.
2. **소식 한 편은 긴 글이 아니라 "빈칸이 채워진 틀"이다.** 질문, 한 문장 답, 대표 숫자, 핵심 3줄, 가져온 이유, 조작형 설명, 오해 방지 한마디, 확인 문제, 낯선 단어, 깊이 읽기(접힘), 출처 순서다.
3. **시안의 코드를 읽어 보니 빈칸은 D-050이 적은 여덟 개보다 많다.** 조작 화면 안의 짧은 단계 이름, 도넛 그림, 대상별 한 줄 설명, 차이 계산도 소식마다 손으로 넣은 것이었다. 이것들을 컴포넌트의 스펙 빈칸으로 넣었고, 숫자 표기와 계산은 모델이 아니라 코드가 한다 (3장).
4. **새는 "가져온 이유"를 말하는 전달자다.** 도착 화면에서 등장하고, 소식을 열 때 가져온 이유를 말풍선으로 건네고, 조작 화면 옆에서 오해 방지 한마디를 하고, 확인 문제에 반응하고, 마지막에 마무리한다. 읽는 동안에는 스스로 움직이지 않는다 (5장).
5. **준비는 하루 한 번, 12단계의 기록형 순차 처리다.** 선정은 규칙이 하고, AI는 판단과 글감만 낸다. 하루 비용은 r2 실측 0.66달러에서 약 0.45달러로 예상한다. 대부분은 "250건에서 3건 고르기"에 들고, 시안 수준으로 꾸미는 글감은 한 편에 0.01달러쯤이다 (6장).
6. **한 가지 언어(TypeScript), 앱 하나, DB 파일 하나.** 만드는 동안은 맥북에서 돌리고, 매일 쓰기 시작하면 작은 서버 한 대로 옮긴다. 폰에서는 홈 화면에 추가해 쓰는 모바일 웹이다 (9장).
7. **가장 큰 미확인은 "틀을 만들면 정말 시안 수준이 되는가"다.** 틀은 아직 만들어진 적이 없다. 그래서 첫 작업은 r2의 저장된 결과를 새 틀에 넣어 폰에서 시안과 견주는 것이고, AI 비용이 들지 않는다 (14장).

## 1. 목표와 설계 원칙

**목표** (D-045): 저비용의 경량 모델로도 목표 시안 수준의 소식을 받게 한다. 세 핵심 가치를 모두 담는다 (D-003).

| # | 원칙 | 뜻 | 근거 |
|---|---|---|---|
| 1 | 틀이 품질을 맡는다 | 구성·디자인·그림·숫자 표기는 고정된 컴포넌트가 한다. 한 번 만들면 매일 AI 비용이 들지 않는다 | D-050, Spike 10.2절 |
| 2 | 모델은 짧은 빈칸만 채운다 | 한 번의 호출에 한 가지 일, 글자 수가 정해진 칸. 경량 모델이 잘하는 크기로 일을 자른다 | D-045 |
| 3 | 사실 목록이 척추다 | 화면에 나오는 사건의 사실·숫자는 모두 사실 ID를 달고, 사실은 기사 원문 문장에 글자 그대로 이어진다 | D-049, FR-C-02, FR-C-15 |
| 4 | 틀릴 수 있는 것은 코드가 한다 | 숫자 표기, 차이 계산, 선정, 프로필 항목의 존재 여부, 출처 표시는 모델에게 맡기지 않는다 | P-04, FR-D-04, FR-B-10 |
| 5 | 단계마다 남기고, 다시 돌릴 수 있다 | 입력·출력·모델·지시문·설정·비용을 단계마다 남긴다. 다시 돌린 결과는 덮어쓰지 않고 나란히 둔다 | NFR-V-01~03, D-047 |
| 6 | 부분 실패는 부분만 뺀다 | 빈칸 하나, 조작형 하나, 새의 움직임이 실패해도 나머지는 전달된다. 글자만 남는 경우는 없다 | NFR-A-01, D-039 |

## 2. 전체 구조

```
[준비 · 하루 한 번]                                        [읽기 앱 · 폰의 모바일 웹]
프로필 스냅숏 → 수집 → 1차 선별 → 사건 정리                 본인 확인(패스키)
 → 사실 목록 → 연결고리 평가 → 선정(규칙)                    → 도착 화면(새 등장, 오늘의 카드)
 → 표현 시트 → 조작형 설명 → 깊이 읽기                        → 소식(틀 + 빈칸, 조작, 확인 문제)
 → 검증·고쳐 쓰기 → 발행 | 보류                 ──발행본──▶   → 새와 마무리 → 종결
        │ 단계마다 결과와 AI 호출 기록                        프로필 관리 · 간단 평가 · 신고 · 지난 소식
        ▼                                                       │
[DB 파일 하나] 실행 기록 · 보도 · 사실 목록 · 결정 · 발행본 · 프로필 · 평가 ◀──┘
        ▲
[개발자용 도구] 기록 열람 · 다시 돌리기 · 나란히 비교 · 누락 표시 · 키워드 기준선 · 지표
```

읽기 앱은 발행된 결과만 읽는다. 사용자가 열었을 때 AI를 부르지 않는다 (NFR-P-01). 준비 프로그램, 읽기 앱, 개발자용 도구는 같은 코드 저장소의 같은 앱 안에 있고, 소식 한 편의 형식 정의를 함께 쓴다.

## 3. 시안에서 배운 것: 무엇이 틀이고 무엇이 글감인가

시안 파일의 코드와 데이터를 읽었다. 시안은 r2의 결과(`DATA`)를 그대로 싣고, 그 위에 세 가지를 얹었다.

| 구분 | 시안에서의 위치 | 내용 | 이 설계에서 누가 맡는가 |
|---|---|---|---|
| ① 화면 틀 | CSS와 그리는 함수 전체 | 배치, 명조 제목, 주제 색, 카드, 진행 막대, 깊이 읽기 전환, 용어 접기, 출처 목록, 어두운 화면 | 고정 컴포넌트 (코드) |
| ② 소식별 글감 | `INFO` 객체 | 질문형 제목, 답 한두 문장, 대표 숫자와 설명, 핵심 3줄, 카드 한 줄, 확인 문제(질문·보기·정답·해설), 주제 이름·색·아이콘 | 표현 시트 (모델) + 주제 색·아이콘은 주제 영역 표 (코드) |
| ③ 조작 화면 안에 손으로 넣은 것 | `stepWorkbench`, `hiringWorkbench` 함수 안 | 단계의 짧은 이름("24주 노출", "18% 흔적"), 18% 도넛과 설명, "연구 대상은 생쥐" 주의 문구, "77 − 39 = 38%p" 차이 계산과 해석 주의, 대상별 한 줄 설명, 눌러 보는 키워드 네 개와 풀이, 카드의 작은 그림 | **D-050에 없던 부분.** 컴포넌트 스펙의 빈칸(모델)과 컴포넌트의 그림·계산(코드)으로 나눈다 |

여기서 나온 설계 판단은 넷이다.

1. **표현 시트만으로는 시안이 나오지 않는다.** 시안의 인상은 ③에서 많이 나온다. 취업 소식의 조작 화면은 그 한 편만을 위한 함수였다. 매일 그렇게 만들 수는 없으므로, 컴포넌트마다 "큰 숫자, 그림, 짧은 이름, 대상별 한 줄, 주의 문구" 자리를 미리 갖추고 스펙에서 채운다.
2. **대표 숫자는 모델이 쓰지 않는다.** "16% → 30%", "38%p"는 사실에 든 숫자로 코드가 만든다. 모델은 어느 사실의 어느 숫자인지와 형태(하나, 전→후, 차이)만 고른다. 38%p는 어느 사실에도 없는 계산값이어서, 모델이 쓰게 두면 틀린 숫자가 들어올 길이 생긴다.
3. **주의 문구는 근거가 있어야 한다.** 시안의 "같은 질문·동일 집단의 결과는 아니다"는 사실 목록에 없는 말이다. 맞는지 확인할 수 없다. 오해 방지 한마디는 사실 ID를 달아야 하고 다른 문장과 같은 검증을 받는다.
4. **시안에서 가져오지 않는 것**: 나중에 읽기와 요약 복사(D-009, PRD 7장), 데스크톱용 옆 목록, "오늘, 한눈에"라는 이름(시안을 만든 모델이 붙인 것). 영어 꼬리표("YOUR DAILY SIGNAL")는 한국어를 기본으로 한다.

**[미확인]** "틀을 갖추면 경량 모델의 글감으로도 시안 수준이 된다"는 시안을 보고 내린 추론이다. 틀은 만든 적이 없고, 창업자가 그 결과를 본 적도 없다. 이 문서 전체가 이 추론에 기대고 있다.

## 4. 소식 한 편의 구조: 틀, 빈칸, 검증

### 4.1 글감 단위

모델이 써서 화면에 나오는 모든 글은 **글감 단위** 하나다. 단위마다 어느 칸의 글인지, 근거 사실 ID, 종류를 가진다.

| 종류 | 뜻 | 검증 |
|---|---|---|
| 사실 | 이 사건에서 일어난 일을 말하는 글 | 사실 ID 필수. 숫자는 코드 대조, 뜻은 다른 모델이 대조 |
| 해석 | 이 일이 무슨 뜻인지에 대한 글. 해석임이 드러나야 한다 | 사실을 인용하면 사실과 같다. 단정하면 반려 |
| 개념 | 배경지식과 용어 풀이. AI가 아는 지식으로 쓴다 (D-042) | 원문 대조 대상이 아니다. 화면에 "AI 지식으로 쓴 설명"으로 구분해 표시. 숫자와 이 사건의 새 사실을 쓰면 반려 |
| 새의 말 | 가져온 이유, 오해 방지 한마디 | 사실을 담으므로 사실과 같은 검증 (FR-C-16). 가져온 이유는 프로필 항목과도 대조 |

Spike에서는 본문 문장만 이 구조였고, 표현 시트와 조작형 설명의 문장은 숫자만 보거나 아예 보지 않았다. 이 설계는 **검사기 하나가 모든 칸을 같은 방식으로 본다.**

### 4.2 고정된 것 (코드와 디자인)

배치와 읽는 순서, 글꼴과 여백, 주제 영역별 색과 아이콘, 순번과 진행 표시, 대표 숫자의 표기와 그림(도넛, 막대, 전→후), 차이·비율 계산, 출처 목록과 기준 시점, 자동 딱지(매체 한 곳의 보도, 주장이 섞임, 짐작이 섞인 연결, 알아 둘 소식, 새로운 분야), 깊이 읽기 접기, 용어 접기, 새의 자리와 움직임, 새의 준비된 대사, 확인 문제의 정답·오답 반응 문구, 어두운 화면.

주제 영역은 정해진 목록에서 고른다 (초기 제안: AI·기술, 과학, 건강, 일·커리어, 경제·돈, 사회·제도, 생활, 문화, 국제, 환경). 목록의 확정은 Evaluation Spec의 일이다 (PRD 0.3절). Spike에서는 모델이 주제를 자유롭게 한 단어로 썼는데, 그러면 "같은 주제는 하루 한 편" 규칙과 주제 색이 표기 차이에 흔들린다.

### 4.3 모델이 채우는 빈칸 (표현 시트)

| 빈칸 | 내용 | 길이 | 근거 | 필수 |
|---|---|---|---|---|
| 질문 | 이 소식의 핵심 긴장을 묻는 한 줄. 제목을 되풀이하지 않는다 | 25자 | — | 필수 |
| 답 | 질문에 대한 이 소식의 답 | 80자 | 사실 ID | 필수 |
| 무슨 일 | 사건을 그대로 말하는 한 줄 (Spike의 제목) | 40자 | 사실 ID | 필수 |
| 대표 숫자 | 형태(하나 / 전→후 / 차이 / 없음), 어느 사실의 어느 숫자, 숫자의 이름 | 이름 20자 | 사실 ID | 선택 |
| 핵심 3줄 | 30초 안에 요점이 잡히는 세 줄 | 각 40자 | 사실 ID | 2줄 이상 |
| 카드 한 줄 | 도착 화면 카드의 한 줄 | 40자 | 사실 ID | 필수 |
| 가져온 이유 | 새가 말하는 추천 이유. 연결고리에 있는 내용만 | 2문장 | 연결고리 ID | 필수 |
| 오해 방지 한마디 | 잘못 읽기 쉬운 점을 막는 한 문장 | 60자 | 사실 ID | 선택 |
| 확인 문제 | 잘못 읽기 쉬운 지점을 묻는 문제, 보기 2개, 정답, 해설 | 해설 100자 | 사실 ID | 선택 |
| 낯선 단어 | 용어와 쉬운 풀이 | 풀이 80자 | 개념 | 1개 이상 |
| 조작형 유형 | 어떤 유형으로 무엇을 보여 줄지와 이유, 또는 조작형이 맞지 않는다는 판단과 이유 | — | 사실 ID | 필수 |

가져온 이유 아래에는 코드가 근거 줄을 붙인다: 내 프로필의 해당 항목 원문과 이 소식의 해당 사실 한 줄. 모델은 둘을 잇는 말만 쓴다. Spike에서 추천 이유가 프로필보다 더 나간 표현으로 검증을 통과한 일이 있었는데(Spike 9장 6번), 프로필 쪽을 코드가 원문 그대로 보여 주면 보탤 자리가 줄고 AC-PR-01이 화면에서 바로 확인된다. **[미확인]**

### 4.4 컴포넌트 목록

| 구분 | 컴포넌트 | 스펙의 빈칸 | 상태 |
|---|---|---|---|
| 조작형 | 비교 | 대상, 항목, 수치(사실 ID), 대상별 한 줄(사실 ID), 계산 항목과 대조값 | **[확인]** 폰에서 동작 (S5a). 대상별 한 줄과 그림은 **[미확인]** |

| 조작형 | 과정 | 단계 제목·짧은 이름(8자)·설명(사실 ID)·수치 | **[확인]** 폰에서 동작, 실제 소식에서 모델이 만든 스펙 2건 통과 (r2). 짧은 이름은 **[미확인]** |
| 조작형 (후보) | 갈래 살펴보기 | 항목 3~5개, 항목별 풀이(사실 ID) | **[미확인]** 아직 없다. 순서가 없는 여러 갈래(전문가 의견 넷 등)를 담을 자리다. Spike에서 모델이 순서 없는 내용을 '과정'으로 만든 문제(9장 7번)의 구조적 대책이다 |
| 조작형 (후보) | 관계 | — | 만들지 않았다. 좁은 화면 배치가 어렵다. 뒤로 둔다 |
| 시각 콘텐츠 | 수치 그림, 핵심 사실 표, 일정표 | 사실 ID만 고르면 코드가 그린다 | 요약 카드만 **[확인]** (S5a). 나머지 **[미확인]** |

컴포넌트 하나는 그리는 코드, 스펙 형식, 검증기, 고정 기술 테스트 사례 2건 이상, 실패 시 대체로 이루어진다. 목록을 늘리는 일은 이 다섯 가지를 함께 더하는 일이다. 서로 다른 조작 방식 2가지 이상(D-025)은 지금 목록으로 충족한다.

유형은 표현 시트 단계에서 정하고, 코드가 전제 조건을 먼저 본다: 비교는 단위가 같은 수치 사실이 둘 이상, 시뮬레이션은 조건과 결과를 잇는 수치 관계, 과정은 실제 순서가 있는 사실 셋 이상. 전제가 서지 않으면 그 유형을 고를 수 없다. 조작형이 맞지 않으면 시각 콘텐츠를 넣고 이유를 남긴다 (FR-D-01, FR-D-15). 조작형을 넣을 수 있는지는 선정 뒤에만 따진다 (FR-B-21).

사진은 쓰지 않는다. 이용 권리를 확인한 사진이 없다 (T-07). 대체 시각 요소는 모두 사실 목록으로 그린다. 생성 이미지도 쓰지 않는다.

**발행 판정 (규칙)**: 필수 칸(질문, 답, 무슨 일, 핵심 2줄 이상, 가져온 이유, 시각 요소 하나)이 통과해야 발행한다. 선택 칸은 실패하면 그 칸만 뺀다. 답이나 무슨 일이 통과하지 못했거나, 걸린 단위가 3분의 1을 넘으면 그 소식을 보류하고 사유를 남긴다 (FR-C-14). 가져온 이유가 끝내 통과하지 못하면 코드가 만든 문장("프로필에 적어 주신 ○○와 이어지는 소식이에요")으로 바꾼다. 보류로 편수가 줄어도 채우지 않는다 (D-028).

검증기가 잡지 못하는 것도 적어 둔다: 사실 목록의 사실 문장이 원문 인용과 뜻이 다른 경우(인용은 글자 그대로지만 사실 문장은 모델이 쓴다), 개념 설명의 오류, 유형 선택이 설명 목적에 맞는지. 앞의 둘은 뜻 대조 단계에 사실 문장과 인용의 대조를 더해 줄인다. **[미확인]**

## 5. 읽기 화면: 구성, 순서, 새

### 5.1 하루 읽기의 흐름

| # | 화면 | 보이는 것 | 새 |
|---|---|---|---|
| 1 | 도착 | 오늘의 소식 카드(주제 색, 카드 한 줄, 대표 숫자, 작은 그림)와 편수. "처음부터 읽기". 카드를 눌러 골라 읽어도 된다 | **등장.** 날아와 앉는 움직임과 준비된 한마디 ("오늘은 세 가지를 가져왔어요") |
| 2 | 소식 머리 | 주제·순번(2/3)·기준 시점, 질문(큰 명조), 답, 무슨 일, 대표 숫자와 그림 | **전달.** 소식을 열면 건네는 움직임을 하고, 말풍선으로 가져온 이유를 말한다. 아래에 근거 줄 |
| 3 | 핵심 3줄 | 카드 세 장 | 위쪽 구석에 작게 앉아 가만히 있는다. 누르면 반응한다 |
| 4 | 직접 해 보기 | 조작형 설명 또는 시각 콘텐츠. 무엇을 바꾸면 무엇을 알 수 있는지 한 줄. 자료와 기준 시점 | 조작 화면 옆에 **오해 방지 한마디**를 말풍선으로 (움직임 없음) |
| 5 | 확인 문제 | 문제 하나, 보기 둘. 답하면 해설 | 답하면 작게 반응한다. 틀려도 부끄럽게 하지 않는 문구 (P-06) |
| 6 | 낯선 단어 | 눌러서 펼치는 풀이. "AI 지식으로 쓴 설명" 표시 | — |
| 7 | 깊이 읽기 | 접혀 있다. 펼치면 사실·개념·해석 딱지가 붙은 본문 | — |
| 8 | 출처 | 매체, 시각, 원문 링크. 자동 딱지 | — |
| 9 | 다음 | "다음 소식". 남은 소식이 없으면 "마무리" | 소식을 마치면 가볍게 반응 (터치 반응 재사용) |
| 10 | 마무리 | "오늘의 소식은 여기까지예요." 더 볼 것은 없다. 조용한 링크 둘: 오늘 소식 다시 보기, 오늘 어땠는지 남기기(선택) | **마무리.** 마무리 움직임과 준비된 한마디. 누르면 계속 반응한다 |

- 기본 화면(1~6, 8)만으로 한 편에 2분 안팎, 세 편에 6분쯤을 목표로 한다 (FR-C-11). 긴 본문은 원할 때만 읽는다. 조작하지 않아도 요점은 핵심 3줄에서 잡힌다 (FR-D-10).
- PRD가 요구하는 요소는 기본 화면에 모두 있다: 핵심 사실(답, 핵심 3줄), 나와의 관계(가져온 이유), 개념 설명(낯선 단어), 출처와 시점. 배경지식의 긴 설명은 깊이 읽기에 있다 (FR-C-03).
- **골라 읽기**: 시안처럼 도착 화면에서 순서를 고를 수 있다. 편수는 정해져 있고 진행 위치(2/3)가 보이며, 다 읽으면 마무리로 간다. 도착 화면에는 "오늘은 여기까지"도 있어 다 읽지 않고 마무리할 수 있다. 재촉은 없다 (FR-F-02~05). 정해진 순서로만 읽게 하던 r2 화면에서 바뀐 점이고, 제품 방향이므로 창업자가 정한다 (15장).
- 같은 날 나갔다 돌아오면 읽던 소식에서 잇는다 (FR-F-06). 마무리 뒤에 다시 들어오면 종결 상태가 유지된다 (FR-F-10).
- 전할 소식이 없는 날과 준비 중인 때에도 새가 나와 준비된 한마디로 알린다 (FR-F-09, D-028).
- 지난 소식은 메뉴 안에 따로 둔다. 날짜별 목록이고, 같은 틀로 조작형까지 다시 볼 수 있다. 읽음 표시와 추천은 없다 (FR-F-12~13).
- 간단 평가와 신고는 마무리 뒤의 별도 화면이다. 읽는 도중에는 묻지 않는다 (FR-G-01~03, D-030).

### 5.2 새

**역할**: 새는 추천 이유의 화자다. "이 소식을 왜 가져왔는지"를 새가 말하면, 전달자(P-06)라는 설정과 근거 있는 추천 이유(P-01)가 한 자리에서 만난다. 본문은 새의 대사가 아니다 (FR-C-16, D-026).

| 순간 (FR-E-01) | 언제 | 움직임 | 말 |
|---|---|---|---|
| 등장 | 도착 화면이 열릴 때 | 등장 | 준비된 대사 |
| 소식 전달 | 소식을 열 때 (사용자가 연다) | 전달 | 가져온 이유 (모델이 쓰고 검증을 거침) |
| 터치 반응 | 새를 누를 때, 확인 문제에 답할 때, 소식을 마칠 때 | 반응 | 없음 또는 준비된 짧은 문구 |
| 마무리 | 마지막 소식 뒤 | 마무리 | 준비된 대사 |

- **읽는 동안에는 스스로 움직이지 않는다** (FR-E-03). 움직임은 모두 사용자가 무언가를 한 직후에만 일어난다. 읽는 중의 새는 화면 위쪽 구석에 작게 멈춰 있고 본문을 가리지 않는다.
- **대사** (D-017): 상황별 대사는 미리 써서 검수한 묶음에서 고른다 (등장·편수별, 마무리, 소식 없는 날, 준비 중). 매일 AI로 만들지 않는다. 출석·연속 기록·질책, 의식이 있는 것처럼 들리는 말, 개인정보를 더 달라는 말이 없는지 한 번 점검하면 된다 (FR-E-05~07). 소식마다 달라지는 말은 가져온 이유와 오해 방지 한마디 둘뿐이고, 둘 다 4.5절의 검증을 받는다.
- **애셋 계약**: 새의 움직임 파일은 다음 입력을 가진 상태 기계 하나로 약속한다: `enter`(등장), `deliver`(전달), `tap`(반응), `bye`(마무리), 그리고 가만히 있는 상태. 이 약속을 지키는 파일이면 그림이 바뀌어도 파일만 갈아 끼운다. 네 순간에 서로 다른 고급 움직임을 요구하지 않는다 (D-026).
- **성능과 실패**: 움직임 도구는 첫 화면이 그려진 뒤에 불러온다. 화면 밖에 있거나 읽는 중이면 그리기를 멈춘다. 움직임을 줄이는 기기 설정이면 멈춘 그림만 보인다 (NFR-U-04). 불러오지 못하면 멈춘 그림으로 바꾸고 읽기는 그대로 되며 실패를 기록한다 (FR-E-09).
- **기술**: Rive를 쓴다 (D-031). 프로토타입(S6)에서 기성 애셋으로 네 순간, 터치 반응, 읽는 중 정지, 실패 대체, 움직임 줄이기가 맥북의 크롬에서 동작했다 **[확인]**. 폰에서는 아직 보지 않았다 **[미확인]** (`docs/research/spikes/rive-bird-prototype.md` 8장).
- **S6에서 배운 것**: (가) Rive 런타임이 지금의 "상태 기계 입력" 방식을 앞으로 없앤다고 예고했다. 위 애셋 계약의 입력 넷은 새 방식(데이터 바인딩)으로 정한다. (나) 우리 새의 그림 파일은 배경이 투명하고 대지를 채워 그려야 한다. 시험에 쓴 기성 애셋은 둘 다 아니어서 둥근 창 안에 잘라 넣었다. (다) 런타임은 압축 전 1.3MB쯤이다. 첫 화면 뒤에 불러오는 것이 전제다. 우리 새의 그림을 누가 그릴지는 비용과 제품의 얼굴에 관한 일이어서 창업자가 정한다 (15장).

## 6. 소식을 준비하는 과정

### 6.1 단계와 입출력

단계마다 결과를 남기고, 다음 단계는 남은 결과만 읽는다. 선정과 글쓰기는 서로 다른 단계다 (FR-C-01). 비용은 3편 발행 기준이고, "r2 실측"은 2026-11-15 하루치 한 번의 값이다.

| # | 단계 | 입력 | 출력 (기록으로 남는 것) | 하는 쪽 | 모델 등급 | r2 실측 → 예상 (달러) |
|---|---|---|---|---|---|---|
| 1 | 프로필 스냅숏 | 살아 있는 프로필 항목 | 이번 실행이 근거로 삼은 항목 목록 (FR-A-11) | 코드 | — | 0 |
| 2 | 수집 | 스냅숏, 공급원, 검색어 | 후보 사건 목록. 후보마다 어느 경로로 들어왔는지 | 코드 + AI(검색어) | 가벼움 | 0.007 → 거의 0 |
| 3 | 1차 선별 | 후보 전체(제목·요약), 프로필 항목 | 모든 후보의 판단과 이유, 깊이 볼 후보 12건 | AI + 규칙 | 가벼움 | 0.124 → 0.035 |

### 6.3 후보를 모으는 길

r2에서 선정된 3편은 모두 프로필에서 나온 검색어로 들어왔고, 공급원의 "큰 사건" 44건에서는 한 편도 뽑히지 않았다 (Spike 9장 1번). 그래서 후보를 모으는 길을 설정으로 여러 개 두고, 후보마다 어느 길로 들어왔는지 남긴다.

- 프로필 검색: 지금의 주된 길.
- 큰 사건: "개인 연결은 약하지만 알아야 할 일"(FR-B-08)과 누락 점검을 위해 적은 양으로 유지한다.
- 주제 영역별 수집: 프로필 검색어에 걸리지 않는 발견형 소식(P-08)을 위한 길. 공급원이 주제별 조회를 주는지 **[미확인]**.

프로필 검색어로 후보를 모으는 것은 수집 방법이지 추천 방법이 아니다. 고르는 일은 5~7번이 한다. 그래도 검색어에 걸리지 않으면 후보가 되지 못하므로, 수집 단계의 누락은 독립 표본 대조로 따로 본다 (FR-G-12, 8.3절).

편집 정책(D-033)은 3번과 6번에 넣는 글 한 편으로 둔다. 지금은 프로필의 "받고 싶지 않은 소식"만 적용하고, 정치적 판단을 코드에 넣지 않는다 (FR-B-18).

### 6.4 하루의 기준과 실패

- **하루 한 판, 저녁에 준비한다** (T-01). 기본값은 매일 18시(한국 시간)다. "하루 일과를 마치고" 읽는다는 제품 정의(B§5)에 맞춘 값이고 설정으로 바꾼다. 새 판이 발행되면 그것이 "오늘의 소식"이 되고, 앞의 판은 지난 소식으로 간다. 알림과 도착 연출은 없다 (D-020).
- r2는 약 2분이 걸렸다. 15분을 넘기면 멈추고 실패로 남긴다. 실패하면 30분 간격으로 두 번 더 해 보고, 그동안 앱은 "준비 중"을 보여 준다.
- 한 번의 실행과 한 달의 AI 비용에 상한을 두고, 닿으면 멈춘다 (6.1절, 15장).
- 소식이 줄거나 없는 날은 원인을 셋으로 나눠 남긴다: 품질 기준, 뉴스 수집, 시스템 (FR-G-11).
- 이미 전달한 사건은 다시 고르지 않는다. 같은 사건에 새 기사가 나와 기존 사실 목록에 없는 핵심 사실이 생겼을 때만 "지난번에 전한 소식의 다음 이야기"로 다룰 수 있다 (T-06). 판단에 넣는 과거 정보는 사건 ID와 사건의 사실뿐이다 (D-048). **[미확인]**

## 7. 전달 뒤의 정정

발행본은 바뀌지 않는다. 고칠 일이 생기면 그 소식의 새 판(리비전)을 만들고 "정정" 표시와 함께 지난 소식에도 반영한다. 내릴 수도 있다 (NFR-T-03, FR-F-13). 계기는 창업자의 신고(FR-G-03)이고 개발자용 도구에서 처리한다. 원문 기사가 고쳐진 것을 자동으로 알아내는 일은 MVP에 넣지 않는다. 발행 전에 사람이 보는 절차도 넣지 않는다. 어떤 경우에 사람이 봐야 하는지는 정책(D-023)이고 창업자가 정한다.

## 8. 저장 구조, 실행 기록, 다시 돌리기

### 8.1 무엇을 저장하는가

DB는 파일 하나(SQLite)다. 한 사람이 쓰는 규모에 맞고, 통째로 복사하면 백업이 되고, 맥북에서도 서버에서도 똑같이 돈다.

| 묶음 | 담는 것 | 비고 |
|---|---|---|
| 실행 | 실행 ID, 판 날짜, 계기(예약·수동·다시 돌리기), 부모 실행, 상태, 시간, 비용, 설정 판, 지시문 판, 코드 판, 프로필 스냅숏 | NFR-V-01, FR-G-10 |
| 단계 결과 | 실행·단계별 결과 한 덩어리(JSON)와 상태 | 다음 단계의 입력이 된다 |
| AI 호출 | 단계, 모델, 지시문 판, 입력이 가리키는 기록, 응답, 토큰, 시간, 비용, 오류 | 프로필 글은 여기에 넣지 않고 항목 ID로만 가리킨다 (10.4절) |
| 보도와 사건 | 매체, 발행 시각, 원문 주소, 본문, 사건 묶음, 들어온 경로 | FR-B-02~03 |
| 사실 목록 | 사건별 사실, 원문 인용, 수치 | 모든 근거의 종착점 |
| 결정 | 후보별 판단, 평가, 선정·제외 이유, 어느 단계에서 빠졌는지 | FR-B-10, FR-B-14 |
| 발행본 | 판, 소식, 리비전, 상태(발행·정정·내림). 틀에 넣을 데이터 전체 | 바뀌지 않는다. 형식 판 번호를 가진다 |
| 프로필 | 항목, 항목의 수정 이력, 스냅숏 | 프로필 글이 있는 유일한 곳 |
| 읽기 | 판별 진행 위치, 화면 요소의 성공·실패, 조작했는지 | 이어 읽기와 평가에만 쓴다. 추천에 쓰지 않는다 (D-021) |
| 평가 | 소식별·세션별 간단 평가, 신고, 누락 표시, 잘못 묶인 사건 표시 | 모델의 자체 평가와 창업자의 평가를 구분 (FR-G-07) |
| 공급원 | 공급원별로 확인한 권리 범위와 상태 | NFR-R-02. 지금은 "미확인" (D-041) |

지난 소식이 오래 지나도 그려지도록, 발행본의 형식은 칸을 더하는 쪽으로만 바꾸고 컴포넌트는 앞선 형식 판을 계속 읽는다 (FR-F-12).

**보관** (T-11): 발행본, 사실 목록, 결정 기록은 지우지 않는다. 기사 원문 본문은 90일 뒤에 지우고 사실 목록의 짧은 인용(15~60자)만 남긴다. 원문 전체를 오래 쌓아 두지 않기 위한 기본값이고 권리 확인(D-012) 때 다시 본다. 90일이 지난 실행은 사실 목록 단계 다음부터만 다시 돌릴 수 있다.

### 8.2 다시 돌리기 (D-047)

- 어느 실행의 어느 단계부터든 다시 돌릴 수 있다. 앞 단계의 저장된 결과를 입력으로 쓴다.
- 다시 돌린 것은 **새 실행**으로 남고 부모 실행을 가리킨다. 당시 결과를 덮어쓰지 않는다. Spike는 같은 폴더에 덮어썼다.
- 모델, 지시문 판, 설정값을 바꿔서 다시 돌릴 수 있다. 고친 뒤에 같은 사례가 달라졌는지 보는 방법이다 (FR-B-15, AC-PR-06).
- 당시 결과와 새 결과를 나란히 보여 준다. 글자까지 같기를 요구하지 않는다.
- 당시의 모델이 더는 제공되지 않으면 대신 쓴 모델을 기록한다. 지워진 프로필 항목이 있었던 실행이면 "당시와 조건이 다름"으로 표시한다 (10.4절).
- 다시 돌린 실행은 발행하지 않는다.

### 8.3 개발자용 도구 (T-05)

## 9. 배치, 플랫폼, 언어와 도구

### 9.1 어디서 돌리고 어디서 읽는가

| 시기 | 준비 프로그램 | 읽기 | 프로필 |
|---|---|---|---|
| 만드는 동안 | 창업자의 맥북 | 폰 브라우저. 확인용 화면은 지금처럼 비공개 페이지로 보낸다 | 맥북의 `private/` |
| 매일 쓰기 시작할 때 | 작은 서버 한 대. 항상 켜져 있고 매일 저녁 스스로 돈다 | 폰의 모바일 웹. 홈 화면에 추가해 앱처럼 연다 | 서버의 DB 파일 (암호화) |

- 서버를 쓰는 이유: 매일 저녁 소식이 준비되려면 항상 켜진 장비가 있어야 한다. 맥북은 덮여 있는 시간이 길고, 창업자에게 항상 켜 둘 다른 장비가 없다. Technical Discovery 4.2절의 대안 B다.
- 서버는 한 대, 프로세스 하나다. 웹 서버, 예약 실행, DB 파일이 같이 있다. 함수 여러 개와 관리형 DB를 엮는 구성(대안 C)은 부품이 많고 긴 AI 호출과 맞지 않아 쓰지 않는다.
- 첫 후보는 Fly.io의 가장 작은 상시 서버와 1GB 디스크(도쿄)다. 한 달 5달러 안팎으로 본다. **[미확인]** 요금과 가입 조건은 옮길 때 확인한다. 가입과 결제는 창업자가 한다. 같은 앱이 맥북에서도 그대로 돌기 때문에 다른 곳으로 옮기기 쉽다.
- 대가는 프로필이 창업자의 장비 밖에 저장된다는 점이다. 보호 방법은 10장에 있고, 받아들일지는 창업자가 정한다 (15장).
- 백업: 서버 디스크의 일별 스냅숏과, 맥북으로 암호화된 사본을 내려받는 명령.

**플랫폼** (D-022): 모바일 웹이다. 조작형 설명은 갤럭시 S23의 브라우저에서 동작했다 **[확인]** (S5a). 새(Rive)는 맥북의 크롬에서 동작했고 **[확인]**, 폰에서는 **[미확인]**이다 (S6). 홈 화면 추가와 전체 화면 실행까지만 넣고 푸시는 넣지 않는다 (FR-F-08). 네이티브 앱은 만들지 않는다.

**네트워크** (T-08): 판 하나(소식 3편의 데이터)는 작아서 처음 열 때 한 번에 받는다. 읽는 도중에 끊겨도 끝까지 읽고 조작할 수 있다. 평가와 프로필 저장이 실패하면 입력을 화면에 남긴 채 알리고 다시 시도할 수 있게 한다 (E-A-01). 연결 없이 처음 열면 안내를 보여 준다.

## 10. 프로필, 접근 제어, 외부 AI에 보내는 개인정보

### 10.1 프로필의 구조 (D-011)

항목 단위다. 항목 하나에 한 가지 사실을 적는다.

| 필드 | 내용 |
|---|---|
| 분류 | 하는 일, 관심사, 생활 맥락, 고민과 계획, 아는·모르는 분야, 받고 싶지 않은 소식 (Spike에서 쓴 여섯 가지) |
| 내용 | 서술형 한 줄. 선택형으로 고른 값도 여기에 글로 남는다 (FR-A-04) |
| 출처 | 직접 입력 / AI 추론. MVP에서는 AI 추론을 프로필에 저장하지 않는다 (Q-10). 추천 과정의 추론은 연결고리에 추론으로 표시된다 (FR-B-09) |
| 민감 여부 | 건강·재정 같은 민감 정보는 MVP에서 받지 않는다 (Q-11, FR-A-09). 입력 화면이 그렇게 안내한다 |
| 다시 볼 날 | 선택. "최근 고민"처럼 시효가 있는 항목에 붙인다. 지나면 프로필 화면에서 확인을 권한다. 스스로 바꾸지 않는다 (E-A-05) |
| 상태와 이력 | 살아 있음 / 지움. 고칠 때마다 판이 남는다. 스냅숏은 항목 ID와 판을 가리킨다 (FR-A-11) |

- 시작에 필요한 최소는 "하는 일" 한 줄과 "관심사" 하나다 (FR-A-02). 나머지는 모두 선택이고, 항목을 더하는 것만으로 넓어진다 (NFR-M-03).
- 폰에서 열람·추가·수정·삭제한다 (FR-A-01, FR-A-05~06). 고치거나 지우면 다음 준비부터 반영되고 화면이 그 시점을 알린다 (FR-A-07).
- Spike는 프로필 글 파일을 문장으로 잘라 항목으로 삼았고, 한 줄에 여러 사실이 든 항목이 한 덩어리로 다뤄졌다. 입력 화면이 "한 항목에 한 가지"로 이끈다.
- 지금 맥북에 있는 프로필 글 파일은 처음 한 번 항목으로 옮긴다.

### 10.2 접근 제어 (T-02)

앱 안의 단일 계정이고, 패스키(폰의 지문 인증)로 연다. 가입 화면과 여러 사용자 체계는 없다 (D-002).

- 처음 한 번, 서버에 넣어 둔 일회용 설정 코드를 입력해 폰에 패스키를 등록한다. 등록이 끝나면 코드는 쓸모가 없어진다. 다른 기기(아이패드, 맥북)도 같은 절차로 더한다.
- 그 뒤로는 지문으로 연다. 외울 비밀번호가 없고, 새어 나갈 비밀번호도 없다.
- 로그인하지 않으면 어떤 화면도 데이터도 나가지 않는다 (E-F-05). 개발자용 화면도 같다.
- 폰을 잃으면 서버에서 등록을 지우고 새 설정 코드로 다시 등록한다.
- 비밀 링크 방식은 쓰지 않는다. 링크가 새면 곧 프로필이 샌다.
- **[미확인]** 갤럭시 S23에서의 패스키 동작은 해 보지 않았다. 문제가 있으면 긴 암호 문구와 오래 가는 로그인 유지로 바꾼다.

### 10.3 저장과 전송의 보호

- 전송은 모두 HTTPS다.
- 서버 디스크는 암호화된 디스크를 쓴다. 그 위에 프로필 글과 가져온 이유처럼 개인 내용이 든 칸을 앱이 한 번 더 암호화한다. 열쇠는 DB 파일과 다른 곳(서버의 비밀값 저장소)에 둔다. DB 파일이나 백업이 새도 읽히지 않게 하기 위해서다 (NFR-S-02, NFR-S-06).
- API 키와 열쇠는 서버의 비밀값 저장소와 맥북의 `.env`에만 있다. Git에 넣지 않는다.
- 로그에는 프로필 글과 응답 본문을 찍지 않는다.

### 10.4 외부 AI에 보내는 범위 (T-03)

| 단계 | 보내는 프로필 내용 | Spike와의 차이 |
|---|---|---|
| 검색어 만들기 | 살아 있는 항목 전부 (프로필이 바뀔 때만) | 실행마다 → 바뀔 때만 |
| 1차 선별 | 항목 전부 | 같음 |
| 사실 목록 | **없음** | 같음 |
| 연결고리 평가 | 항목 전부 | 같음 |
| 표현 시트 | 그 소식의 연결고리에 쓰인 항목만 | 새 단계 |
| 조작형 설명 | **없음** | 같음 |
| 깊이 읽기 | 연결고리에 쓰인 항목과 "아는·모르는 분야" 항목만 (설명 수준을 맞추는 데 필요) | 전부 → 일부 |
| 뜻 대조 | 연결고리에 쓰인 항목만 | 같음 |

- **보내지 않는 것**: 이름, 연락처, 주소 같은 직접 식별 정보와 민감 정보. 프로필에 적지 않는 것이 규칙이고, 저장할 때 전화번호·이메일·주민번호 꼴의 글자를 코드가 찾아 알린다.
- **보내는 곳**: 지금은 Google의 Gemini API 유료 등급 한 곳이다. 2026-11-15에 공식 문서에서 확인한 내용: 유료 등급에서는 입력과 응답을 Google의 제품 개선에 쓰지 않는다. 오남용 감시를 위해 한정된 기간 기록을 보관한다. 보관 기간의 정확한 날수와, 프로젝트의 요청 기록 저장 설정이 켜져 있는지는 **[미확인]**이다. 창업자의 AI Studio 설정 화면에서 확인해야 한다.
- 다른 회사의 모델(Claude, GPT)에 프로필을 보내기 전에는 그 회사의 조건을 같은 방식으로 확인하고 창업자에게 다시 묻는다.
- 이 범위를 받아들일지는 창업자가 정한다 (15장). S7(개인정보 조사)은 수행하지 않았고, 위 내용이 그 대신이 되지는 않는다.

### 10.5 지운 프로필 정보 (D-048, D-034)

**다시 쓰이지 않게 막는 것** (확정된 요구, FR-A-07):

1. 연결고리의 프로필 근거는 이번 스냅숏에 살아 있는 항목 ID만 인정한다. 코드가 막는다. **[확인]** r2
2. 과거 이력으로 넣는 것은 사건 ID와 사건의 사실뿐이다. 과거의 추천 이유와 개인화 문장은 다시 입력하지 않는다.
3. 프로필이 바뀌면 저장해 둔 검색어를 버리고 다시 만든다. 지운 항목에서 나온 검색어가 남는 길을 막는다. (이 설계에서 새로 생긴 길이어서 함께 막는다.)

**과거 기록에 남은 내용을 어떻게 할 것인가** (D-034, 창업자 결정): 제안은 "가린다"이다.

- 프로필 글은 한 곳(프로필 항목의 이력)에만 있고 다른 기록은 항목 ID로 가리킨다. 그래서 지울 때 그 한 곳의 글을 지우면 스냅숏과 AI 호출 기록에서도 함께 사라진다. 항목이 있었다는 사실(ID, 분류, 지운 날)만 남는다.
- 그 항목에서 나온 글(가져온 이유, 연결고리의 설명, 선별 이유)은 연결고리가 항목 ID를 달고 있어서 찾을 수 있다. 찾아서 가린다. 지난 소식에서는 가져온 이유 자리에 "지운 프로필 항목에 근거한 이유여서 가렸어요"가 보인다. 그 호출의 응답 원문은 지운다.
- 그 실행은 "지워진 항목이 있어 당시와 같은 조건으로 다시 돌릴 수 없음"으로 표시된다. 나머지 항목과 사건의 사실로는 다시 돌릴 수 있다.
- 다른 길(전부 그대로 보존, 실행 기록째 삭제)과 견주면, 삭제를 실제로 지키면서 실패 사례의 구조는 남는다.
