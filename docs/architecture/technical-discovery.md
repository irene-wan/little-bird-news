### 0.1 다시 묶은 진행 순서

1. **S5a 인터랙티브 시험 페이지** (진행). 가짜 내용으로 조작형 설명 세 가지와 실패 시 대체를 폰에서 확인한다.
2. **실뉴스 공급원 하나 확보** (S1 축소판). 창업자가 가입해 키를 넘긴다.
3. **핵심 가치 프로토타입** (S2·S3·S4·S5b를 하나로 묶음). 실뉴스 → 사건 묶기 → 내 프로필과의 연결고리로 고르기 → 근거를 단 집필 → 인터랙티브 붙이기 → 폰에서 읽기까지 하루치를 끝까지 만든다. 단계마다 기록을 남겨 무엇이 왜 뽑혔는지 볼 수 있게 한다. 브리프는 공급원이 확보되면 올린다.
4. **새** (S6). Rive 프로토타입을 읽기 화면에 붙인다. 프로토타입에는 이용 조건을 확인한 기성 Rive 애셋을 쓰고, 우리 새의 그림은 그 뒤에 정한다.
5. 정책과 규약(권리 확인, 개인정보 정책, 편집 정책, 합격선)은 프로토타입을 써 본 뒤에 정한다.

### 0.2 엔지니어가 고른 구조 (방향 6에 따른 선택, 창업자가 뒤집을 수 있음)

- **프로토타입 단계**: 소식을 준비하는 프로그램은 창업자의 맥북에서 돌린다. 결과는 폰 브라우저에서 여는 웹 페이지로 본다. 기록은 맥북 안의 파일 DB 하나에 둔다. 프로필은 맥북 밖에 저장하지 않는다(AI 호출 때 필요한 내용만 전달).
- **매일 쓰는 단계**: 작은 호스팅 앱 하나로 옮긴다 (4.2절의 B).
- **도구**: 한 가지 언어(TypeScript)로 준비 프로그램과 읽기 화면을 함께 만든다. 인터랙티브 스펙의 형식을 만드는 쪽과 그리는 쪽이 같은 정의를 쓰게 하기 위해서다. AI 모델은 프로토타입에서 한 공급사의 모델로 시작하고, 단계별 모델과 비용은 기록한다.
- **프로토타입의 개인정보 임시 규칙**: 건강·재정 같은 민감 정보는 프로필에 넣지 않는다 (PRD Q-11의 작업 가정과 같다). 이름·연락처 같은 직접 식별 정보는 AI에 보내지 않는다.

**결정 상태** (Decision Log v1.3): 창업자 방향 D-040~D-046은 Confirmed. 엔지니어가 고른 구조 D-047~D-051은 Proposed. D-011~D-023, D-033, D-034는 여전히 Pending 또는 Validation Required다. 이번 Spike는 그 어느 것도 확정하지 않았다.

**프로토타입을 다시 돌리는 법** (저장소 루트에서, Node만 있으면 된다)

1. `.env`에 `NEWSAPI_AI_KEY`, `GEMINI_API_KEY`가 있어야 한다 (`.env.example` 참고). 프로필은 `private/profile.md`. 둘 다 Git에 없다.
2. `node spikes/core-prototype/run.mjs <실행ID>`: 수집부터 오늘의 소식까지. 단계 결과는 `private/runs/<실행ID>/`에 남고, 다시 실행하면 이미 끝난 단계는 건너뛴다. `--from=<단계>`로 그 단계부터 다시 돌린다.
3. `node spikes/core-prototype/render.mjs <실행ID>`: 폰 읽기 화면(`spikes/core-prototype/dist/`)을 만든다.
4. `node spikes/core-prototype/present.mjs <실행ID>`: 표현 시트를 모델별로 만들어 본다 (읽기 화면에는 연결되지 않았다).
5. 설정(소식 수, 평가 비중, 단계별 모델, 비용 상한)은 `spikes/core-prototype/config.json`, 지시문은 `spikes/core-prototype/lib/prompts.mjs` (버전 p3)에 있다.

비용: LLM 누적 약 0.98달러(Gemini 선불 잔액 약 8,000원 중), 뉴스 토큰 약 67 / 2,000. `private/`의 실행 기록은 이 맥북에만 있다.

**다음에 할 일 (제안, 순서대로)**

1. **Technical Design 초안** (`docs/architecture/technical-design.md`): D-047~D-051과 Spike에서 배운 점(Spike 문서 9장)을 입력으로 쓴다. 이 문서가 승인되어야 아키텍처가 확정된다.
2. **읽기 화면을 목표 시안 방향으로 다시 설계**한다 (D-045, D-050). 화면 틀이 품질의 큰 몫이므로 Technical Design에서 가장 무게를 둘 부분이다. 표현 시트를 `run.mjs`의 정식 단계로 넣고 읽기 화면에 연결하는 일이 남아 있다.
3. **경량 모델 비용 낮추기**: 비용의 대부분이 앞 단계(선별·사실 목록·평가)에서 나온다. 이 단계에 더 가벼운 모델을 쓰는 비교가 필요하다. Claude와 GPT 모델은 키를 받으면 비교한다.
4. **새(S6)**: 세 핵심 가치 가운데 유일하게 손대지 않았다. MVP는 세 가치를 모두 요구한다 (D-003).
5. 실행하지 않은 지시문 변경(p3의 6~8번), 날짜 반복 실행, S7, Evaluation Spec(D-018), 편집 정책(D-033).
6. 이후는 기능별 Spec → Plan → Task → Implement → Test → Review (Product Brief 14). Spike 코드는 제품 코드로 가져다 쓰지 않는다.

## 1. 목적

Product Definition과 MVP PRD가 승인되었고, 기술 스택과 아키텍처는 미확정이다 (B§13, PRD 8장). Brief 14장의 3단계(뉴스 데이터 이용 권리·추천 파이프라인·인터랙티브 UI·Rive에 대한 Technical Spike)에 들어가기 전에 다음을 정리한다.

- 무엇이 기술적으로 불확실한가 (3장)
- 어떤 구조 대안이 있는가 (4장)
- 어떤 Spike로 무엇을 검증하는가 (6장)

결과는 이후 Technical Design(`docs/architecture/technical-design.md`)과 Decision Log 변경안의 입력이 된다.

## 4. 아키텍처 대안

### 4.1 대안과 무관한 공통 논리 구조 (Proposed)

```
[준비 파이프라인 · 배치]                                   [읽기 앱 · 모바일]
수집 → 사건 정리 → 후보 평가 → 선정 → 사실 목록·집필       접근 제어 → 오늘의 소식 → 읽기+조작
  → 인터랙티브/시각 구성 → 발행 전 검증 → 발행 | 보류   ──▶  새(Rive) · 마무리 · 지난 소식
        │  단계마다 산출물+결정 기록+실행 메타                   프로필 CRUD · 간단 평가/신고
        ▼                                                          │
[기록 저장소] 공급원 레지스트리 · 보도 · 사건 · 결정 기록 ◀────────┘
  · 사실 목록 · 소식/리비전 · 스펙 · 프로필 항목 버전 · 평가
        ▲
[개발자용 평가 도구] 기록 열람 · 누락 표시 · 독립 표본 대조 · 재실행 · 기준선 비교 · 지표 집계
```

단계 구성은 PRD 2.7절의 "소식이 준비되는 과정"을 따른다. 아래 설계 아이디어는 모두 Proposed이며 Spike로 검증한다.

- **검증된 사실 목록을 척추로 삼는다.** 사건마다 원문 위치가 붙은 사실·숫자 목록을 먼저 만든다. 연결고리의 사건 쪽 근거, 본문 문장, 인터랙티브 수치가 모두 이 사실 ID를 참조한다. 숫자와 인용은 코드로 대조하고, 의미는 독립 검증 모델로 확인한다 (FR-B-07, FR-C-02, FR-C-15, FR-D-04~05).
- **연결고리는 구조화 기록이다.** 프로필 항목 ID, 사건 사실 ID, 관계, 추론 여부, 설명을 담는다. 프로필 쪽 근거는 준비 시점 스냅숏의 살아 있는 항목 ID만 참조하도록 코드로 강제한다. 삭제한 정보의 재사용(차단 조건)을 LLM의 출력에 맡기지 않고 구조로 막는다 (FR-A-07, FR-A-11, FR-B-06).
- **선정 구성은 결정적 규칙이다.** LLM은 평가와 근거를 내고, 수량·다양성·중복·새로움에 따른 구성은 설정값 기반 코드가 맡는다. 선정·제외 이유를 재현할 수 있다 (FR-B-10~11, NFR-M-01). 인터랙티브 적합성은 선정 이후 단계에서만 계산한다 (FR-B-21).
- **발행물은 불변 스냅숏과 정정 리비전이다.** 읽기 앱은 발행된 것만 읽는다 (C1, C7).

### 4.2 시스템 배치 대안 (T-10, D-022)

| 대안 | 내용 | 장점 | 단점·위험 |
|---|---|---|---|
| A. 로컬 우선 | 파이프라인·DB·앱을 창업자 장비에서 실행하고, 폰은 사설망으로 접속 | 프로필이 내 장비에만 있다. 비용이 가장 적다. 접근 제어가 망 수준이다 | 장비가 꺼지면 소식이 없다. 폰에 VPN이 필요하다. 운영 안정성이 낮다 |
| B. 단일 호스팅 앱 (모듈형 모놀리스) | 웹 서버 + DB + 예약 배치 워커 하나. 모듈 경계는 파이프라인/읽기 API/평가 도구로 나눈다 | 항상 켜져 있다. 구성이 단순하다. 1인 운영에 맞다. 같은 코드로 로컬 재실행이 가능하다 | 프로필이 클라우드에 저장된다(보호 설계 필요). 소액 고정비가 든다 |
| C. 서버리스 조합 | 정적 호스팅 + 관리형 DB + 함수/예약 워크플로 | 운영 부담이 적다 | 구성 요소가 많다. 긴 LLM 배치와 함수 시간 제한이 충돌한다. 로컬 재현과 추적이 어렵다 |
| D. 하이브리드 | 파이프라인·기록·평가 도구는 로컬, 발행물만 얇은 클라우드 읽기 앱으로 | 실험과 재실행이 빠르다. 클라우드 노출이 적다 | 프로필·피드백(폰→로컬)과 발행물(로컬→폰)의 양방향 동기화가 필요하다. 환경이 둘이다 |

**제안 (Proposed): B.** 개인정보를 내 장비 밖에 두지 않는 것이 최우선이면 A다. 최종 판단은 S7 결과와 5장의 창업자 입력에 따른다.

## 6. 제안하는 Technical Spike

공통 규칙 (CLAUDE.md 「Technical Spike 예외」):

- Spike마다 목적·범위·검증 기준을 담은 브리프를 창업자가 승인한 뒤 시작한다.
- 코드는 제품 코드와 분리된 `spikes/<주제>/`(제안)에 두고, 결과와 한계는 `docs/research/spikes/<주제>.md`에 기록한다.
- 결과는 기술 선택을 자동으로 확정하지 않는다.
- Spike의 검증 기준은 MVP 합격선(D-018)이 아니며 Evaluation Spec을 대신하지 않는다.
- 각 Spike는 처리시간과 비용을 함께 기록한다 (T-09).

| Spike | 검증 Gate·결정 | 범위 | 검증 기준 (브리프에서 확정) | 선행 | 브리프 |
|---|---|---|---|---|---|
| S1 뉴스·사진 공급원 권리 조사 | F-01, D-012, T-07, T-11 | 코드 없는 조사. 국내 공급원 후보의 약관·계약 조건 확인 | 공급원별 권리 매트릭스, 제공 필드, 최신성, 비용. 1차 산출은 실험에 써도 되는 데이터 | 없음 | `docs/research/spikes/news-source-rights.md` |
| S7 개인정보·접근 제어·프로필 모델 | F-07, T-02, T-03, D-034, D-011 | 조사와 설계안. AI 공급사 데이터 조건, 접근 제어 비교, 삭제와 재실행의 선택지, 프로필 항목 모델 초안 | 실제 프로필을 쓰기 전에 필요한 임시 전달 규칙을 창업자가 정할 수 있는 근거 자료 | 없음 | `docs/research/spikes/privacy-access-profile.md` |

| S5b 인터랙티브 스펙 생성 | F-05, D-016 | S4의 사실 목록에서 LLM이 유형을 고르고(이유 기록) 스펙을 생성. 수치·계산 검증. 부적합 판단 시 정적 시각 콘텐츠 | 스펙 유효율, 주입한 수치 오류 검출, 가정값 구분 표시, 유형 선택 이유 기록 | S4, S5a | 3차에 작성 |
